## 이미 실행한 검증과 한계

- 실제 스테이징 DB를 `BEGIN READ ONLY`로 조회: `yearend_tax_params(2025)` 존재, SQL 260과 같은 카드번호 사전검사 네 범주의 건수 0(등록 카드 6, 거래 757). 원문 번호와 거래는 출력하지 않았다.
- 스테이징의 **226~232 적용 후 스키마**를 `pg_dump --schema-only`로 읽어 격리 PostgreSQL 17에 복원했다. 이 PC의 로컬 PostgreSQL에는 `pgvector`가 없어 복제본에서 해당 확장·인덱스만 제외하고 무관한 임베딩 열을 text로 치환했다. 나머지 스키마는 그대로 사용했다.
- 로컬에만 `yearend_tax_params(2025)` 기준 행을 추가해 242의 FK를 충족했다. **실제 스테이징 데이터 전체를 복사해 시험한 것은 아니다.**
- 새 격리 DB에서 226~232 재적용 7/7, 이어서 위 순서의 나머지 21/21이 통과했다. **별도 새 DB에서 실제 재개 명령과 같은 21개만** 적용해도 21/21이 통과했다. 두 경우 모두 설치 뒤 일곱 정의 검사가 통과했고, 최종 계약 JSON 7개가 DB 함수 투영·계약 해시와 일치했다.
- 설치 후 별도 트랜잭션에서 무관 카드 열 추가·카드전표 인덱스 제거·무관 계정과목 열 추가를 시도하면 해당 정의 검사가 각각 거절됐다(3/3). 시험 트랜잭션은 롤백됐고 최종 검사는 다시 통과했다.
- 완성 후 **처음부터 28개를 또 재적용하는 것은 실패한다.** 격리 DB에서 241의 과거 단계 정의 검사가 후속 설치 상태와 충돌했고, 앞 파일을 다시 실행하면 최종 정의도 깨진다. 현재 스테이징 재개 명령에는 226~232를 다시 넣지 않는다. 이 파일 단위 단계 계약과 복구 절차가 충분한지 검토해 달라.
