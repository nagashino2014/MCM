# 사용 매뉴얼·`?` 도움말 구축 계획 (2026-10-20)

> 근거 조사: [manual-help-survey-2026-10-20.md](manual-help-survey-2026-10-20.md) (화면 인벤토리·연계표·도움말 후보·결함 목록)
> UI 기준: [ui-precision-standard.md](ui-precision-standard.md) §3(설명문과 `?` 도움말). 기존 `CdHelp`·`CdPageHeader help=`를 그대로 쓴다.
> 상태: **1차 커밋(7f6f8923)·2차 구현 완료(2026-10-20, 브랜치 `claude/user-manual`)**, 미배포 — 결정 D-1~D-6 권장안 승인

## 0. 목표와 원칙

1. 직원이 "이 화면에서 뭘 하지?"를 느끼는 순간 **지금 보고 있는 화면의 설명**이 한 번에 열린다.
2. 설명은 **사용자 시각**으로 쓴다. 코드·내부 용어 대신 화면의 버튼 이름을 그대로 쓰고, "누르면 어디에 무엇이 반영되는가"를 적는다.
3. **내 권한으로 볼 수 없는 장은 보이지 않는다.** 메뉴 노출과 같은 판정(`menuPermissionKeys` + `hasAnyPerm`)을 쓴다.
4. **기능이 바뀌면 매뉴얼이 같이 바뀌어야 한다.** 매뉴얼은 별도 문서가 아니라 코드와 같은 저장소의 데이터이고, 화면과 어긋나면 테스트가 실패한다(§5).
5. 새 라이브러리를 들이지 않는다. 마크다운 파서 없이 TypeScript 데이터 + 기존 cdash 컴포넌트로 렌더한다.
6. 기존 화면 구조는 바꾸지 않는다. 추가하는 것은 상단바 버튼 1개, 매뉴얼 드로어·전용 페이지, 제목·필드 옆 `?` 버튼뿐이다.

## 1. 사용자 경험

### 1.1 상단바 "사용 매뉴얼" 버튼

- 위치: `TopBar.tsx`의 **[+ 새로 작성] 바로 오른쪽**, 할 일 알림 앞.
- 모양: 보조 버튼(`cd-btn`, 반경 8px `--mcm-action-radius`), `BookOpen` 아이콘 + "매뉴얼" 글자(`sm` 미만은 아이콘만), `aria-label="사용 매뉴얼"`.
- 새 소식 표시: 마지막으로 본 업데이트 이후 변경 기록이 있으면 버튼에 작은 점. 본 시점은 `localStorage`(try/catch, 없어도 정상 동작).
- 단축키: `F1`(브라우저 도움말 대신 앱 매뉴얼을 연다). Ctrl K 전역 검색에도 매뉴얼 기사가 함께 검색된다.

### 1.2 매뉴얼 드로어(현재 화면 기준)

버튼을 누르면 오른쪽 드로어(`CdDrawer side="right"`, 폭 약 520px)가 열린다.

```
┌ 사용 매뉴얼 ─────────────────── [전체 매뉴얼 ↗] [×] ┐
│ [ 매뉴얼 검색…                                    ] │
│ ── 지금 보고 있는 화면 ───────────────────────────── │
│ 계약 관리                     업데이트 2026-10-20     │
│  이 화면에서 할 수 있는 일 · 5줄                       │
│  ▸ 신규 계약 등록하기                                  │
│  ▸ 청구·수금 단계와 발행/수금 기록                      │
│  ▸ 전자세금계산서 발행  ⚠ 되돌릴 수 없음               │
│  ▸ 변경계약 입력(새 차수/보완/정정)                     │
│ ── 관련 업무 시나리오 ─────────────────────────────── │
│  계약 등록부터 수금까지 / 월말 미수 점검               │
│ ── 새로 바뀐 것 ─────────────────────────────────── │
│  10-20 매뉴얼 기능 추가                                │
└──────────────────────────────────────────────────┘
```

- 현재 경로(+`?tab=`)를 `resolveMenuRoute`와 같은 "가장 구체적인 경로 우선" 규칙으로 기사에 매칭한다. 메뉴 밖 화면(기안 작성, 할 일 상세 등)도 기사의 `routes`에 등록해 매칭한다.
- 매칭 기사가 없으면 "시작하기"와 검색창을 보여 준다.
- 드로어는 화면 위에 겹쳐 열려 작업 중인 입력을 잃지 않는다.

### 1.3 전체 매뉴얼 페이지 `/manual`

- 경로: `/manual`(목차), `/manual/[articleId]`(기사). 사이드바 메뉴에는 넣지 않는다(구조 보존). 버튼·검색·`?`의 "자세히" 링크로만 들어온다.
- 왼쪽 목차: 사이드바와 같은 그룹 순서(시작하기 → 홈 → 협업 → 업무 → 사업 운영 → 관리 → 부록), 권한 없는 장은 숨김.
- 상단 탭: **전체 / 내 역할 추천 / 업무 시나리오 / 새로 바뀐 것**.
- 각 기사 하단: "이 화면 열기" 링크(권한이 있을 때), 관련 기사, 업데이트 일자.
- 인쇄 스타일: 장 단위 인쇄 → PDF 저장으로 **직원 교육 배포본**을 만들 수 있다.

### 1.4 화면 안 `?` 도움말

- 기존 규칙 유지: 클릭·Enter로 열고 Esc로 닫는 360px 팝업, 대상 이름이 붙은 라벨("전자발행 도움말").
- 짧게 3~6줄로 핵심만 쓰고, 끝에 **"매뉴얼에서 자세히 →"** 링크를 달아 드로어의 해당 절로 이동한다.
- 경고·필수 조건·실행 영향(예: "발급하면 취소할 수 없습니다")은 `?` 안에 숨기지 않고 화면에 남긴다(UI 기준 §3). `?`에는 그 이유와 대안을 적는다.
- 페이지 단위 설명은 `CdPageHeader help=`, 필드·버튼 단위는 해당 요소 옆 `<CdHelp>`.

### 2.2 데이터 모델 — `frontend/content/manual/`

```ts
// content/manual/types.ts
export type ManualBlock =
  | { kind: "p"; text: string }                      // 문장. 버튼 이름은 ui("…") 로 감싼다
  | { kind: "steps"; items: string[] }               // 번호 단계
  | { kind: "tip" | "warn"; text: string }           // 팁 / 되돌릴 수 없는 동작 경고
  | { kind: "table"; head: string[]; rows: string[][] }
  | { kind: "flow"; text: string }                   // "이 작업을 하면 → 어디에 반영" 연계
  | { kind: "link"; article: ArticleId; label?: string };

export interface ManualSection { id: string; title: string; blocks: ManualBlock[]; requires?: readonly string[] }

export interface ManualArticle {
  id: ArticleId;                 // 안정 키(예: "contracts.manage"). 메뉴 이름이 바뀌어도 유지
  chapter: ChapterId;
  title: string;
  routes: string[];              // 매칭 경로(예: "/contracts", "/finance?tab=vat")
  requires?: readonly string[];  // 생략 시 routes[0] 로 menuPermissionKeys 조회
  audience: ("staff" | "head" | "exec" | "admin")[];
  summary: string;               // "이 화면에서 할 수 있는 일" 3~5줄
  sections: ManualSection[];
  keywords: string[];            // 검색용 동의어(예: "세금계산서", "계산서 발행")
  sources: string[];             // 이 기사가 설명하는 컴포넌트 파일 — 갱신 감지용(§5)
  reviewedAt: string;            // YYYY-MM-DD, 마지막으로 화면과 대조한 날
}

export interface HelpTopic {
  id: HelpTopicId;               // 예: "contracts.taxInvoice.issue"
  label: string;                 // "전자발행 도움말"
  blocks: ManualBlock[];         // 3~6줄
  more?: { article: ArticleId; section?: string };
  sources: string[];
}

export interface ChangelogEntry {
  date: string; kind: "신규" | "개선" | "변경" | "수정";
  title: string; body?: string;
  articles: ArticleId[];         // 권한 필터에 그대로 사용 — 볼 수 없는 기능 소식은 숨김
}
```

- `ui("변경계약 입력")` 헬퍼는 렌더 시 버튼 모양 글자로 표시되고, 테스트에서는 **화면 문자열 대조 대상**이 된다(§5.2).
- 그림은 1차에서 넣지 않는다(화면이 바뀌면 바로 낡는다). 필요한 곳만 3차에서 자동 캡처(§6 3차)로 추가한다.

## 3. 권한 반영

- 기사·절·도움말·변경 기록 모두 `requires`(없으면 `routes[0]`의 `menuPermissionKeys`)를 `hasAnyPerm(session perms)`로 판정한다. 사이드바와 같은 기준이라 "메뉴에는 없는데 매뉴얼에는 있다"가 생기지 않는다.
- 한 기사 안의 관리자 전용 절(예: 메일 설정의 "인원별 용량 배분")은 절 단위 `requires`로 숨긴다.
- 메뉴는 보이지만 API가 막는 화면(조사 F-1~F-4)은 **매뉴얼 기준을 실제 API 권한으로** 둔다. 메뉴 권한 정리는 별도 작업으로 분리한다(§7).

## 4. `?` 도움말 배치 계획

조사 문서 §3의 통합 우선순위를 그대로 따른다.

| 차수 | 범위 | 개수 | 방식 |
|---|---|---|---|
| P1 | 직원 다수 화면 + 되돌릴 수 없는 동작 (#1~20) | 20 | `HelpTopic` 작성 → 해당 위치에 `<CdHelp topic>` 삽입 |
| P2 | 부서장·관리자·산식 (#21~45) | 25 | 동일 |
| P3 | 재무·영업 전문·운영자 설정 | 약 30 | 동일 + 본문 안내 문단 중 "사용법·배경"만 `?`로 이동(UI 기준 §3 허용 범위, 경고·실행 영향 문단은 유지) |
| 공통 | 헤더 help가 없는 화면 약 25곳 | — | 페이지 단위 `helpTopic` 추가(기사 summary와 연결) |

배치 규칙: 같은 화면에 `?`는 헤더 1 + 필드 최대 4~5개. 그 이상 필요하면 매뉴얼 절로 보내고 `?`에서 링크한다.

## 5. 기능 추가·변경에 따라가는 갱신 체계 ★

앞으로도 기능이 계속 바뀌므로, "사람이 기억해서 고친다"에 기대지 않고 **누락이 드러나는 구조**로 만든다.

### 5.1 단일 원천 + 안정 키
- 기사·도움말은 `id`로 참조한다. 메뉴 이름이 바뀌면 `title`만 고치고 링크는 깨지지 않는다.
- 화면 코드는 도움말 문장을 직접 갖지 않고 `topic` 키만 가진다 → 문장 수정은 `content/manual`에서만.

### 5.2 자동 검사 `npm run test:manual` (기존 `test:menu-route` 방식: esbuild → `node --test`)

| 검사 | 실패 조건 | 잡아내는 상황 |
|---|---|---|
| 메뉴 커버리지 | `MENU_ITEMS`의 모든 href·submenu href에 기사가 없음 | 새 메뉴를 추가하고 매뉴얼을 안 씀 |
| 화면 커버리지 | `app/(app)/**/page.tsx` 경로가 어떤 기사 `routes`에도 없고 `MANUAL_EXCLUDED_ROUTES`(사유 필수)에도 없음 | 메뉴 밖 새 화면 |
| 도움말 키 | 코드의 `topic="…"`이 레지스트리에 없음 / 레지스트리 항목이 어디서도 안 쓰임 | 오타, 화면 삭제 후 남은 도움말 |
| 기사 링크 | `link`·`more`·changelog `articles`가 없는 id를 가리킴 | 기사 통합·이름 변경 |
| **화면 문자열 대조** | 기사·도움말의 `ui("…")` 라벨이 `sources` 파일 어디에도 없음 | **버튼 이름이 바뀌었는데 매뉴얼은 옛 이름** |
| 권한 키 | `requires`의 키가 `MENU_PERMISSION_KEYS`·권한 카탈로그에 없음 | 권한 개편 후 남은 옛 키 |

### 5.3 낡은 기사 보고 `node scripts/manual-staleness.mjs`
- 각 기사·도움말의 `sources` 파일에 대해 `git log -1 --format=%cs`를 읽어 `reviewedAt`보다 최근에 바뀐 것을 "검토 필요" 목록으로 출력한다(실패가 아니라 보고).
- 배포 전에 한 번 돌려 목록이 비어 있거나, 남은 항목이 "화면 동작 변화 없음"인지 확인한다.

### 5.4 변경 기록(직원에게 알리기)
- 기능을 추가·변경하는 커밋은 `content/manual/changelog.ts`에 한 줄을 추가한다(`kind`·`title`·관련 `articles`).
- 매뉴얼 버튼의 점, "새로 바뀐 것" 탭, 드로어 하단에 노출된다. 권한 없는 기능 소식은 보이지 않는다.
- 큰 변경은 기존처럼 게시판 공지도 하되, 공지 본문에 매뉴얼 기사 링크를 붙인다.

### 5.5 피드백(선택, 3차)
- 기사 하단 "도움이 되었나요 / 틀린 내용 알리기". 받는 곳 후보: ① 게시판 피드백 글로 연결(DB 변경 없음) ② `manual_feedback` 표 신설(마이그레이션 필요). 오픈 테스트 기간은 ①을 권장.

### 5.6 작업 규칙(CLAUDE.md에 추가할 문안)
> **매뉴얼 동기화(2026-10-20 사용자 요청):** 화면·버튼·흐름을 추가·변경하는 커밋은 같은 커밋에서 `frontend/content/manual`의 해당 기사·도움말을 고치고 `reviewedAt`을 갱신하며, 사용자에게 보이는 변화는 `changelog.ts`에 한 줄을 남긴다. 커밋 전 `cd frontend && npm run test:manual`이 통과해야 한다. 새 화면은 기사를 쓰거나 `MANUAL_EXCLUDED_ROUTES`에 사유와 함께 등록한다.

- 추가로 `docs/manual-authoring-guide.md`(문체·용어·블록 사용법·예시 기사 1편)를 두어 어느 세션이 써도 같은 문체가 되게 한다.
- 선택: `staging-deploy-next.ps1`에 `test:manual` 실행을 경고 단계로 추가(배포 스크립트 변경이라 별도 승인 후).
