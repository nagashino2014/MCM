# 통합허가 업종 — 앱·백엔드 KSIC 차이표 (2026-11-01)

통합허가 대상 업종을 `permit_industries`(325) 하나로 합치는 작업의 ④단계 자료다. 백엔드 `backend/app/ieps/integrated_permit_industries.py`의
`TARGET_INDUSTRIES`(35개 공식 업종명, 연간보고서 파서·`ksic_llm_reviewer.py` AI 후보)를 표에서 읽게 바꾸기 전에, 코드 차이와 결정할 점을 정리한다.
**결정(2026-11-01 사용자): 모두 KSIC 11차로 통일** — §4 에 스테이징 조회 결과와 반영 내용을 적었다. §3 의 나머지 결정(발전 범위·넓은 접두·백엔드 출력 이름)은 아직 열려 있다.

## 2. ⚠ KSIC 개정 차수 문제(가장 먼저 결정)

앱 업종 매핑과 백엔드 항목의 코드는 **KSIC 10차** 체계다(202=비료, 203=합성고무·플라스틱, 1711·1712=펄프·종이).
그런데 코드표 파일 `data/ksic/ksic11.json`·`frontend/public/ksic11.json`과 백엔드 연간보고서 파서의 코드 보강은 **KSIC 11차(2024)** 다. 11차에서는

| 코드 | 10차 | 11차 |
|---|---|---|
| 202xx | 비료 및 질소화합물 | **합성고무·합성수지·플라스틱 물질**(20201·20202·20203) |
| 203xx | 합성고무 및 플라스틱 물질 | **비료·농약**(20311~20313·20321·20322) |
| 204xx | 농약(2041)·도료(2042)·세제·화장품(2043)·기타(2049) | 도료(2041)·세제·화장품(2042)·기타(2049) — 세분 번호가 바뀜 |
| 171xx | 1711 펄프·1712 종이 | 17101~17109 |

그래서 11차 코드가 들어온 사업장은 지금도 잘못 분류된다(이번 변경 전부터 있던 결함). 예: 11차 20202(합성수지) → 앱 '비료', 11차 20311(화학비료) → 앱 '유기화학'.
계약 화면의 **업종 조회** 버튼은 11차 코드표로 검색하므로 같은 오판정을 보여 준다. 백엔드의 10차 코드 20301·20302·20431~20433·17121~17129 는 11차 코드표에 없다.

## 3. 결정할 점

1. **사업장 마스터 KSIC 코드의 차수** — 스테이징 `facilities.industry_code` 에 10차·11차가 섞여 있는지 읽기 전용 조회로 먼저 확인할지.
   제안: 업종 표에 코드를 **차수별로**(10차·11차) 둘 수 있게 열을 나누고, 사업장 코드 차수를 알 수 없으면 두 체계가 겹치지 않는 코드만 판정에 쓴다.
2. **발전** — 원자력·수력·태양력(11차는 풍력 포함)을 통합허가 대상 '발전'으로 셀지. 제안: 백엔드(법령 표기)대로 화력 35113·기타 35119 로 좁힌다.
3. **유기화학·무기화학·기타화학의 넓은 접두(2011\*·203\*·2012\*·204\*)** — 백엔드처럼 세부 코드로 좁힐지, 앱처럼 접두를 유지할지.
4. **백엔드 출력 이름** — 연간보고서 파서는 지금 공식 업종명(35개)을 돌려준다. 통합 후 ① 앱 업종 이름(20→28개)으로 바꿀지, ② 공식 업종명을 업종 표의 별칭으로 두고 계속 공식명으로 돌려줄지.
5. **백엔드 '기초화학물질 201\*' 항목** — 별도 업종 없이 유기·무기화학 코드로 흡수할지.

결정 후: 업종 표에 필요한 열(예: 코드 차수)을 다음 번호 마이그레이션으로 추가하고, 백엔드는 같은 DB 표를 읽는 조회 함수(캐시 + 표가 없으면 지금 목록)로 바꾼 뒤 `backend/tests`(test_annual_report_parser 등)로 확인한다.

## 5. 남은 데이터 전수 정비(2026-11-01 사용자 요청)

조회 때 문제였던 사업장 약 110곳을 다음과 같이 나눴다(326 적용 후 기준).

- **자체 정비 — 327 `facility_industry_selffix`, 44곳**: 규칙으로 확정되는 것만 넣었다.
  업종명 표기 차이 정리(35300 등), 326 이 바꾼 코드의 업종명을 11차 이름으로, 11차에서 이름만 바뀐 코드(20119),
  코드는 원래 맞고 업종명만 백엔드 공식 업종명인 것(17902 위생용 종이제품 8곳·20311/20312 비료 4곳·22299), 업종명과 정확히 같은 11차 코드가 있는 것(24110 → 20129).
  사업장마다 "지금 값이 조회 때 값과 같을 때만" 바꾸고 전후 값을 `facility_industry_fixes` 에 남긴다.
  리허설(스테이징 코드 1,357곳·실제 사업장 ID): 44곳 적용, 재적용 추가 변경 0, 정비 후 다시 분류하면 남는 문제가 아래 65곳과 정확히 같다.
- **사용자 결정 — 65곳**: 합성고무/합성수지 구분(27), 종이 세부 업종(28), 개별 확인(10 — 형식 이상 코드·업종명 '도금'·코드와 업종명이 다른 업종 등).
  사업장명·사업자번호가 들어가므로 저장소에 넣지 않고 세션 공유 노트(`facility-industry-decisions-2026-11-01.md`)에 두었다. 결정을 받으면 같은 방식(지금 값 확인 후 변경·기록)으로 다음 번호 마이그레이션을 만든다.
- 업종 분류(통합허가 업종)는 결정과 관계없이 이미 바르게 나온다 — 결정은 세부 코드·업종명의 정확성 문제다. 예외: C2·C9('도금')와 C1(전자부품/플라스틱)은 결정에 따라 업종 분류가 바뀐다.
