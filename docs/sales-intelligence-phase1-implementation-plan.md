# RAG 영업 발굴 1차 확장 구현 계획서

작성일: 2026년 10월 30일  
상태: 1차 기능 범위 확정에 따른 구현 계획  
대상: 영업 및 마케팅의 RAG & 영업 발굴 메뉴와 연계 수집 기능

> 구현 기준 보충(2026-10-30): 이 문서는 승인된 범위의 원본 계획이다. 실제 구현은 최신 main `32d7a5c5`와 사용자가 제공한 [KESI Frosted 디자인 기준](kesi-frosted-design-system-reference.md)을 기준으로 진행했다. 아래의 이전 운영 동결·revision 관련 설명보다 최신 저장소 운영 지침이 우선한다. 실제 검증 결과와 적용 조건은 [구현·검증·운영 적용 안내](sales-intelligence-phase1-validation-rollout.md)에 기록한다.

관심 업종·지역·규모·정보 유형에 맞는 정기 브리핑을 자동 생성하고, 중요한 변화가 실제 영업 검토와 후속 활동으로 이어지도록 확장한다. 1차 범위는 정기 브리핑 기본 기능, 영업 실행 연결 F01~F07, 공개 공식 정보원 보강이다. 기존 사업장·영업·계약·보고서·알림 기능을 활용하되, 프로젝트 단위 정보 통합과 정기 실행의 신뢰성을 먼저 확보한다.

기능 구현과 운영 활성화의 완료 기준을 구분한다. 정보원별 인증·이용 조건, 실제 응답, 수집 상태를 검증한 뒤 자동화를 활성화한다. 이 계획서의 수치와 운영 기본값은 별도 표기가 없는 한 구현 및 시범운영을 위한 제안값이다.

## 1 목표와 1차 범위

### 1.1 사용자가 얻게 될 결과

1. 관심 분야를 한 번 설정하면 매일·3일마다·매주·매월 브리핑을 받는다.
2. 이전 보고서 이후의 신규 투자, 추진 단계 변경, 지연·취소를 구분해서 본다.
3. 개별 투자정보와 업종별 산업동향을 함께 확인한다.
4. 기존 사업장에 등록되지 않은 신규 기업·공장도 검토할 수 있다.
5. 서비스 수요의 근거와 미확인 사항을 보고 우선 접촉 대상을 결정한다.
6. 기존 영업건 연결 또는 신규 영업건 생성 후 담당자와 예정 활동을 등록한다.

### 1.2 범위표

| 구분 | 1차 포함 범위 | 완료 상태 |
|---|---|---|
| B01 관심 프로필 | 복수 프로필, 조건·수신자·보고 수준·주기·활성 상태 | 저장한 조건이 미리보기와 정기 실행에 동일하게 적용 |
| B02 정기 실행 | 실행 예약, 수집 상태 확인, 재시도, 중복 방지, 일시중지 | 동일 회차의 보고서가 중복 생성되지 않고 실패를 추적 |
| B03 정기 보고서 | 전체 대상 집계, 전회 대비 변화, 산업동향, 주요 후보, 출처 | 집계·근거·발행본을 재현 가능 |
| B04 전달과 이력 | 앱 수신함·알림·이메일·PDF, 열람 권한, 발행본 관리 | 수신자별 전달 상태와 접근 권한 확인 |
| B05 운영 관리 | 소스 신선도, 실행·비용 현황, 실패·재처리 | 수집·분석·전달 오류를 서로 구분 |
| F01 중요 변화 알림 | 조건별 신규 중요 사건·변경·취소 알림 | 수집 후 확인된 중요 사건의 우선 전달 |
| F02 투자 프로젝트 통합 | 여러 출처의 같은 사업 연결, 단계·금액·일정 이력 | 기사 수와 실제 투자 건수를 구분 |
| F03 신규 사업장 검토 | 미매칭 후보의 검토·기존 연결·신규 등록·보류 | 기존 마스터 미등록으로 인한 발굴 누락 해소 |
| F04 서비스 수요 추천 | 통합허가·화관법·HAPs·ESG·기타의 검토 가능성 | 사실·가설·확인 과제 구분 |
| F05 우선순위 | 설명 가능한 항목별 평가와 수동 조정 | 점수 근거·누락 정보·버전 표시 |
| F06 영업 및 계약 연결 | 기존 건 연결, 신규 영업건 전환, 중복 방지 | 영업건과 투자프로젝트의 관계 추적 |
| F07 후속 조치 | 담당·기한·행동 제안 및 기존 영업활동 등록 | 제안 채택부터 예정·완료·취소까지 연결 |
| 공개 공식 정보원 | 통계·법령·산업 해설·관심 기업 발표 | 소스별 검증 후 활성화, 미활성 사유 표시 |

F08 이후의 기존 고객 갱신 추천, 방문 전용 브리핑, 지도, 경쟁 분석, 전사 성과 분석, 수행 인력 배정, 수익 예측은 후속 범위다. F01~F07에 필요한 기존 고객·담당자·계약 요약 조회는 포함한다. 유료 시장 DB, 모든 업종·기업의 전수 수집, 법적 의무 자동 확정, 고객에게 보내는 외부 영업메일 자동 발송은 1차에 포함하지 않는다.

### 2.1 그대로 재사용할 수 없는 부분

- 현재 generateBriefing은 검색 상위 24건을 사용하고, 건별 문맥을 700자로 제한한다. 정기 브리핑은 조건 전체의 집계 결과와 주요 프로젝트의 충분한 근거를 구성하는 별도 경로로 구현한다. 수동 질의 경로는 호환성을 유지한다.
- 뉴스·보도자료·EIASS·커스텀 수집의 일부 저장 경로는 동일 외부 식별자에 대해 삽입을 건너뛴다. 같은 URL의 정정이나 사업 진행 상태 변경을 추적하려면 문서 버전 관리가 필요하다.
- 기존 브리핑 sources는 주로 출처 메타데이터다. 정기 보고서의 근거 문서 버전과 사용한 발췌·집계를 고정해야 한다. 기존 refineBriefing의 동일 행 덮어쓰기를 정기 발행본에 적용하지 않는다.
- 기존 공유 테이블은 수신함과 읽음 표시용이며, 보고서 전체의 객체별 접근제어를 보장하지 않는다. 목록·상세·PDF·추가 분석·공유 경로에 공통 권한 검사를 추가한다.
- 입찰 알림의 프로세스 메모리·마지막 발송키만으로 다중 실행자의 중복 생성이나 수신자별 부분 실패를 처리하지 않는다. 새 실행·전달 원장을 사용한다.
- 현재 영업 전환은 영업건 생성과 신호 연결이 별도 트랜잭션이다. 신규 경로에서는 하나의 거래로 처리하고 기존 전환도 같은 내부 함수를 사용하도록 정비한다.
- 홈의 work-plan-todo는 업무보고 미제출 등을 조회하는 기능이다. work_tasks는 비계약 업무 프로젝트이므로 연락·방문 과제마다 생성하지 않는다. F07의 확정 활동은 기존 sales_activities에 저장한다.

## 3 화면과 사용자 흐름

### 3.1 메뉴 구성

기존 RAG & 영업 발굴 안에서 다음 화면을 연결한다. 수집 어댑터·인증키·실행 로그 등 운영 설정은 기존 API & 스크래핑 영역을 확장한다.

| 화면 | 주요 내용 | 주요 행동 |
|---|---|---|
| 브리핑 | 수동 AI 질의, 정기 발행본, 공유받은 보고서 | 조회, 출처 확인, PDF, 추가 분석 |
| 관심 설정 | 프로필 목록, 조건, 주기, 수신자, 다음 실행 | 미리보기, 저장·활성화, 지금 생성, 일시중지 |
| 영업 발굴 | 프로젝트별 후보, 우선순위, 관련 서비스, 기존 영업 상태 | 검토, 기존 건 연결, 새 영업건 생성 |
| 신규 사업장 검토 | 미매칭 기업·공장, 유사 기존 사업장, 검토 상태 | 연결, 등록, 보류, 제외 |
| 프로젝트 상세 | 사건 이력, 원문, 금액·일정 변경, 서비스 평가, 연결·활동 | 연결 수정, 병합·분리, 후속 활동 채택 |

임원용 브리핑 첫 화면에는 핵심 변화, 우선 검토 후보, 필요한 의사결정을 먼저 제시한다. 상세 근거와 전체 후보 목록은 펼쳐 볼 수 있도록 한다. 사용자 화면의 명칭은 ‘실행 대기’, ‘일부 자료 지연’, ‘새로운 주요 변동 없음’처럼 업무 용어를 사용한다.

### 3.2 관심 프로필

| 설정 | 동작 및 기본값 |
|---|---|
| 이름·소유자·공유 | 개인 또는 지정 수신자 공유. 개인은 생성자만 열람, 공유는 명시한 활성 사용자로 제한 |
| 업종 | 기존 업종 체계와 사용자 별칭 연결. 같은 조건 안에서는 복수 선택 OR |
| 지역 | 사업장 소재지 기준 시도·시군구·산단 선택. 본사 주소로 자동 대체하지 않음 |
| 규모 | 프로젝트 투자액을 우선 지원하고, 기업 매출·시설 규모는 값과 근거가 있는 경우 별도 필터. 규모 미상 포함 기본 ON |
| 유형 | 신설·증설·이전·공정전환·투자계획·인허가·착공·가동·지연·취소·관련 입찰 |
| 기업·서비스 | 관심 기업·사업장 및 통합허가·화관법·HAPs·ESG·기타 선택 |
| 조건 결합 | 업종·지역·규모·유형 등 서로 다른 조건군은 AND. 포함·제외 및 미상 포함 규칙을 화면에 표시 |
| 주기 | 매일, 기준 시작일부터 3일 간격, 지정 요일 매주, 지정일 매월. 시간대 Asia/Seoul |
| 월말 | 29~31일이 없는 달에는 그 달 마지막 날 실행. 휴일 자동 이월은 1차 제외 |
| 분석 기간 | 기본은 직전 회차 이후 변화. 배경 동향은 최근 3개월, 통계 추세는 확보된 기간 사용 |
| 보고 수준 | 핵심 요약 또는 상세. 동일 집계·근거를 사용하고 표현 분량만 조정 |
| 무변경 처리 | 앱에 무변경 이력 저장, 이메일·푸시는 기본 생략. 사용자가 무변경 안내 수신 선택 가능 |
| 채널 | 앱 수신함 기본, 이메일·모바일 푸시 선택. 수신자는 조직의 사용자 계정에서 선택 |
| 실행 시각 | 설정 시각은 생성 시작 예정 시각으로 표시. 정상 부하에서 15분 이내 발행 목표 |

프로필 저장 시 예상 대상 수·대표 후보·적용된 조건·다음 실행 시각을 미리 볼 수 있게 한다. 미리보기는 기본적으로 AI를 호출하지 않는다. 업종·지역 등 핵심 조건 변경 시 버전을 올리고 다음 회차는 ‘관심 조건 변경 후 첫 보고서’로 표시하여 기존 조건과 잘못 비교하지 않는다.

### 3.3 정기 보고서 구성

보고서는 핵심 요약, 전회 대비 변화, 산업동향, 우선 검토 프로젝트, 서비스 수요와 확인사항, 권장 후속 조치, 출처·집계 범위·수집 상태 순서로 구성한다. 프로젝트별로 ‘확인된 사실 / 서비스 관련 가능성 / 추가 확인사항’을 구분한다.

전체 대상 프로젝트 수와 분석에 사용한 자료 수를 표시한다. 본문에 모두 설명하지 않은 프로젝트는 전체 목록으로 제공한다. 근거 부족·수집 지연·분량 제한이 있으면 해당 범위를 표시하고, 확인하지 못한 내용을 완전한 분석으로 표현하지 않는다.

## 4 F01부터 F07까지의 상세 동작

### 4.1 F01 중요 변화 알림

관심 프로필에 중요 알림을 별도 ON/OFF로 둔다. 새 대형 투자, 인허가·착공 등 주요 단계 진전, 투자액·일정의 중요한 변경, 사업 중단·취소, 연결된 입찰의 마감 임박을 지원한다. 중요도는 사용자 금액 기준·단계·관심기업 조건으로 판정한다.

알림은 문서 수집 후 정규화·프로젝트 연결·사건 확인을 마친 시점부터 평가한다. 정상 처리에서 확인 후 15분 이내 전달을 목표로 한다. 원문 발표 순간부터 실시간 탐지를 보장하지 않으며, 기존 하루 1회 수집 소스의 탐지 지연은 별도로 표시한다.

동일 사건의 재보도는 새 알림을 만들지 않는다. 정정은 원알림과 연결해 변경 내용을 알린다. 여러 프로필이 같은 수신자에게 같은 사건을 전달할 경우 한 알림으로 묶고 해당 프로필을 표시한다. 기본 조용한 시간은 22시~07시이며, 중요한 예외 알림은 사용자가 선택한다. 알림 상한 초과분은 묶음으로 제공하고 사건 자체를 버리지 않는다.

수집·분석 실행을 live, initial_backfill, replay로 구분한다. 최초 90일 소급 적재와 규칙 변경에 따른 재분석은 개별 중요 알림을 기본 억제하고 첫 브리핑에 ‘기존 자료 초기 분석’으로 묶는다. 재분석만으로 과거 사건이 새 사건이 되지 않도록 사건 식별자를 유지한다. 운영 중 새롭게 확인된 실질 정정·추진 사건만 중요 알림 규칙을 적용하며, 오래된 발표의 단순 지연 발견은 기본적으로 다음 브리핑의 보충 항목에 표시한다.

### 4.2 F02 투자 프로젝트 통합

기업·실제 사업장·지역·사업 내용·시기·외부 사업번호를 이용해 출처들을 연결한다. 법인, 사업장, 투자 프로젝트, 당사의 영업건은 서로 다른 대상으로 관리한다. 한 기사에 여러 사업이 포함되면 여러 프로젝트에 연결할 수 있다.

명확한 외부 사업번호 또는 검증된 동일 사업장·사업의 조합은 자동 연결하고, 명칭만 유사하거나 지역·금액이 충돌하는 건은 검토 대상으로 둔다. 같은 기업의 다른 공장을 이름이나 사업자번호만으로 합치지 않는다. 병합·분리 기능은 원문·기존 연결·담당자의 판단 이력을 보존한다.

MOU, 계획 발표, 투자 결의, 인허가, 착공, 가동, 지연, 중단·취소를 사건으로 기록한다. 출처끼리 충돌하면 서로 다른 주장과 확인 필요 상태를 보여준다. 그룹 전체 투자액과 개별 공장 투자액은 범위를 구분하며 중복 합산하지 않는다. 당사 용역 예상금액은 외부 투자액과 완전히 분리한다.

### 4.3 F03 신규 사업장 검토

유효한 신호인데 사업장과 매칭되지 않은 경우 신규 사업장 후보를 생성한다. 이름·주소·업종·운영사·사업자번호의 값마다 출처와 미확인 상태를 보관한다. AI가 주소나 사업자번호를 추정하여 확정 정보로 채우지 않는다.

상태는 신규, 검토 중, 기존 사업장 연결, 신규 등록, 보류, 제외로 둔다. 보류에는 이유와 재검토일, 제외에는 사유를 기록한다. 기존 수동 사업장 등록의 검증을 재사용하되 후보 확정과 관련 신호·프로젝트 연결까지 원자적으로 처리한다. 등록 전에 동일 후보·기존 사업장·동시 등록 여부를 다시 검사한다.

마스터에 등록하기 전에도 후보는 브리핑과 발굴 화면에 나타난다. 사업장 생성은 담당자가 검토한 후 facility.edit 권한으로 수행하며, 영업건 생성은 시설 연결 이후 진행한다.

### 4.4 F04 서비스 수요 추천

업종·시설 변화·프로젝트 단계·확인된 기존 허가 및 계약 요약을 근거로 서비스별 검토 가능성을 제시한다. 최초허가·변경허가·변경신고·사후관리·화학안전·HAPs·ESG 등을 구분하되 법적 적용 여부는 전문가 확인 과제로 남긴다.

서비스 제안마다 근거 문서, 관련 사실, 추론 이유, 필수 확인 질문, 정보 기준일, 규칙·모델 버전을 저장한다. 공개 자료만 사용한 공통 평가와 권한이 있는 내부 자료로 보강한 평가를 분리한다. 내부 평가의 결론·추천 서비스 자체도 내부정보로 취급한다. 근거가 없으면 ‘판단 자료 부족’으로 표시한다. 법령 자료가 추가되더라도 1차는 관련 변경의 참고 및 확인 질문 제공까지이며 F11의 고객별 규제 영향 자동 판정으로 확대하지 않는다.

사업장의 integrated/chemicals/haps/esg/other, 영업의 integrated_permit/chem/esg/etc, 계약의 한글 분류 사이에 명시적인 매핑을 둔다. 1차에서 영업 대분류에 haps를 추가해 HAPs를 손실 없이 전달한다. 기존 키와 기존 분류는 유지하고, 과거 ‘기타’를 자동 재분류하지 않는다. 알 수 없는 키는 저장 오류 또는 검토 상태로 처리하며 조용히 기타로 바꾸지 않는다.

### 4.5 F05 설명 가능한 우선순위

초기에는 이력 학습이나 AI 수주확률 대신 규칙 기반 평가를 사용한다. 기본 가중치는 서비스 적합성 30, 추진 단계 25, 접촉 시급성 20, 기존 관계 15, 확인된 사업 규모 10으로 제안한다. 공개 본문은 공개 근거만으로 계산한 점수와 순위를 사용하며 기존 관계 항목은 포함하지 않는다. 공개 기준 점수는 최대 85점임을 표시하고, 내부 관계의 최대 15점 보정과 내부 자료에 따른 재평가는 권한 있는 부록·화면에서만 제공한다. 항목 정의·배점과 규칙 버전을 관리하고 시범운영에서 조정한다.

근거 신뢰도는 총점과 별도로 표시한다. 누락 항목은 ‘정보 부족’으로 남기고, 확인된 점수와 가능한 범위를 보여준다. 핵심 항목인 서비스 적합성·추진 단계가 미확인인 후보는 확정 순위와 분리한 검토 목록에 둔다. 수동 우선순위 조정은 사유·담당자·시각을 기록한다.

같은 입력과 같은 규칙 버전은 같은 점수를 산출해야 한다. 검색 유사도, 외부 투자금액, AI의 자유로운 숫자를 수주확률이나 예상 용역금액으로 사용하지 않는다.

### 4.6 F06 기존 영업 및 계약 연결

프로젝트 상세에서 사용자가 열람할 수 있는 기존 영업건·계약·담당자를 제시한다. 동일 사업장·서비스·업무범위·진행 시기가 가까운 열린 영업건을 먼저 보여주되, 최종 연결은 사용자가 확정한다. 하나의 투자프로젝트에 서비스·차수별 영업건 여러 개를 연결할 수 있다.

신규 영업건 생성 시 사업장·제목·서비스·담당·우선순위를 확인한다. 예상 용역금액은 기본 미입력으로 두고 외부 투자액을 복사하지 않는다. 계약은 기존 계약을 연결·조회하며 자동 신규 생성하지 않는다.

전환 요청은 멱등 키와 프로젝트 버전을 사용한다. 투자프로젝트·사업장·서비스·업무범위를 잠근 후 기존 연결을 다시 확인하고, 영업건·멤버·인텔 연결·해당 기회의 전환 상태·선택한 최초 활동·감사 기록을 같은 트랜잭션에서 처리한다. 이미 열린 DB 핸들을 받는 내부 생성 함수를 분리해 중첩된 독립 커밋을 피한다. 전송은 커밋 후 처리한다.

전환 상태의 원본은 투자프로젝트·서비스별 연결이다. 한 신호에 여러 투자프로젝트가 연결되어 있으면 하나를 전환했다고 신호 전체를 converted로 숨기지 않는다. 기존 intel_signals의 단일 영업건 링크와 전환 상태는 관계가 명확한 1대1인 경우만 호환용으로 갱신한다. 새 발굴 목록은 연결된 기회별 미전환 여부로 조회하며, 복수 연결은 상세에서 모두 표시한다. 기존 단일 신호 전환 API도 같은 규칙을 적용한다.

기존 전환 완료 신호를 새 프로젝트 모델로 이관할 때는 이미 연결된 영업건을 먼저 복원한다. 불명확한 연결은 검토 상태로 남기고 기존 영업건을 삭제·재생성하거나 미전환으로 되돌리지 않는다.

### 4.7 F07 후속 조치

제안에는 권장 행동, 담당자 후보, 기한, 확인 질문, 근거 사건·브리핑을 담는다. 기존 영업 담당자와 부서를 우선 제안하되 사용자가 변경할 수 있다. 미채택 제안은 영업 일정에 표시하지 않는다.

채택 시 담당·기한·활동 종류를 검증하고 기존 sales_activities에 status=planned로 등록한다. 기존 생성 함수의 기본값인 done을 사용하지 않고 occurred_at도 비워 둔다. 최초 영업건 생성과 함께 채택할 때는 F06과 같은 트랜잭션에 포함한다.

전화·메일처럼 기한만 있는 활동은 확정한 기한을 예정시각으로 저장하고 종료시각도 같게 둔다. 방문·현설·투찰처럼 시간 범위가 필요한 활동은 기존 일정 입력에서 시작·종료를 확정한다. 기존 영업단계의 일정 기반 정책은 유지하되 취소 활동은 단계 계산과 단계 태그에서 제외한다. 기한이 지난 planned 활동은 ‘기한 경과 미완료’로 표시하고, 접촉 완료·제안 완료 등 실제 수행 집계에는 done 활동만 포함한다. 일정상 진행 단계와 실제 활동 완료를 구분하여 보여준다.

이후 완료·취소·일정 변경은 기존 영업활동을 원본으로 삼고 새 상태를 이중 관리하지 않는다. 기한 경과·담당 미지정 중요 활동은 권한 있는 관리자 화면에 표시한다. ‘메일 연락’ 활동 등록이 실제 고객 메일 발송을 실행하지 않도록 구분한다.

### 5.2 소스별 완료 판정

S01·S02·S03 운영 활성화와 S04의 최소 2개 회사 채널 활성화를 1차 소스 보강의 목표로 한다. 기업 후보가 조건을 충족하지 못하면 검증된 다른 공식 기업 채널로 대체한다. 대체도 불가능한 경우 해당 항목을 미완료로 보고하며 활성 채널 수를 부풀리지 않는다. S05·S06은 참고 링크 등록과 상태 표시를 기본 완료 범위로 하고, 자동 수집은 별도 이용 허용이 확인된 경우에 추가한다.

소스 상태는 검증 대기, 인증 대기, 이용 조건 확인 대기, 활성, 일시중지로 표시한다. 인증정보는 기존 비밀정보 저장 방식을 사용한다. 허용되지 않은 원문을 임시 저장·벡터화하여 우회 처리하지 않는다. 자료 형식이 바뀌면 해당 소스만 중지하고 오류·누락을 보고한다.

채널별 최근 10건 또는 최근 90일 전체 중 적은 수를 대조한다. 표본이 없거나 필요한 투자 사례를 확보하지 못하면 허용 범위 안에서 과거 기간을 넓혀 검증 자료를 확보한다. 확보할 수 없으면 운영 검증 대기로 두며 0건 검증을 통과로 기록하지 않는다. 통계는 최근 3개 시점과 전년 동기를 비교하고, 법령은 현행·시행예정·일부개정·무변경 사례를 확인한다. 자동 접근 제한과 호출량을 지키고 HTML·승인된 텍스트 PDF부터 지원한다. 스캔 PDF OCR과 회원 로그인 수집은 1차 기본 범위에서 제외한다.

KOTRA, SEMI, WSTS, 디스플레이협회, 건축HUB, 공장등록 추가 자료, PRTR의 전수 적재는 후속 후보로 남긴다. 기존 입찰과 IEPS 자료의 연결은 신규 수집원 구축이 아니라 내부 데이터 재사용으로 처리한다.

## 6 데이터와 분석 구조

### 6.1 처리 순서

수집 및 버전 저장 → 문서 유형 분리 → 기업·사업장·투자프로젝트 연결 → 사건·서비스·우선순위 평가 → 관심 조건 적용 → 전체 집계 및 근거 고정 → 보고서 생성·검증 → 발행·전달 → 영업건 및 활동 연결 순서로 처리한다.

문서 유형은 투자 사건, 산업동향, 통계, 정책·법령으로 구분한다. 산업동향을 기존 신설·증설 판별기로만 처리하여 제외하지 않는다. 기존 intel_signals와 등급은 유지하고, 새 문서 계층과 연결한다. 모든 통계·법령 자료를 영업 후보로 만들지 않는다.

### 6.3 기간과 변경 감지

- 예정 회차와 사건 분석 기간은 작업 선점 시 고정한다. 근거 스냅샷의 수집 기준시각은 수집 대기가 끝난 뒤 고정하여 대기 중 도착한 자료도 사용할 수 있게 한다. 그 기준시각 이후 들어온 자료는 다음 회차에서 처리한다.
- 신규 발견·정정 판정에는 최초 발견 및 버전 발견 시각을 사용한다. 발표일만으로 다음 회차를 찾지 않는다.
- 분석 기간 안의 사건과, 이번에 늦게 발견한 과거 사건을 구분한다. 과거 사건을 현재 기간의 신규 투자액으로 더하지 않는다.
- 이미 반영한 revision 원장과 겹치는 재조회 기간을 함께 사용한다. 수집 실패 소스의 미반영 자료가 다른 소스의 성공 때문에 건너뛰어지지 않도록 한다.
- 정기 회차의 성공한 분석 또는 정상 무변경 처리만 정기 반영 원장을 전진시킨다. 실패·예산 차단은 완료로 처리하지 않는다. 수동 ‘지금 생성’과 추가 분석은 기본적으로 정기 반영 원장·비교 기준을 전진시키지 않으므로 다음 정기 회차에서 필요한 변화를 누락하지 않는다.
- 주요 조건이 바뀌면 비교 기준을 새로 설정하고, 이전 조건의 건수 증감과 혼합하지 않는다.
- 정정·원문 삭제·404는 별도 상태다. 원문 삭제를 곧바로 사업 취소로 해석하지 않는다.

### 6.4 생성과 검증

기간 전체 집계와 증감률은 SQL·코드로 계산한다. AI에는 검증된 집계, 프로젝트별 사실과 변화, 승인된 산업동향 근거를 제공한다. 긴 보고서는 문서 분할·근거 검색을 사용하고, 모든 문서의 전문을 매 회차 입력하지 않는다.

구조화 출력에 대해 필수 필드, 인용 ID 존재, 숫자·단위·기간 일치, 사실/추정 표시를 검증한다. 핵심 수치·근거가 검증되지 않거나 출력이 잘리면 발행을 보류하고 제한된 횟수만 재시도한다. 중요 사건은 유사도 순위 때문에 빠지지 않도록 필수 포함 규칙을 둔다.

보고서 생성 이후의 메일 실패는 보고서를 재생성하지 않고 전달만 재시도한다. 정기 추가 분석은 원본을 보존하는 새 발행본으로 저장하며 자동 재배포하지 않는다. 정상 무변경은 AI 호출 없이 이력을 저장한다.

## 7 정기 실행과 전달 안정성

### 7.1 실행 구조

기존 매일 03시 수집 배치는 유지하고, 정기 브리핑용 별도 배치 엔트리를 추가한다. 기존 tick-cache는 단일 서버 프로세스의 메모리 캐시이며 S3 공유 기능은 없다. 기본 실행안은 기존 가벼운 tick에 신규 공유 실행예정 캐시를 연결하고, 실행할 일이 있을 때만 전용 ECS 배치를 기동하는 구조다. 공유 저장소는 S3를 후보로 두되 0단계에서 비용·동시 갱신·복구·실행 권한을 검증해 확정한다. 프로필마다 개별 EventBridge 스케줄을 생성하지 않는다.

캐시는 유휴 상태의 불필요한 DB 접속을 줄이는 용도이며, 실행·권한·중복 판정의 원본은 DB다. 다음 작업 시각은 정기 회차, 중요 사건 대기, 수집 대기 재검사, 작업 재시도, lease 회수, 전달 재시도 중 가장 이른 시각이다. 프로필 변경과 작업 상태 변경 시 캐시를 갱신하고, 만료·갱신 실패·프로세스 재시작 시 복구한다. 동시 갱신으로 더 이른 작업 시각이 덮이지 않게 버전 또는 조건부 갱신을 사용한다. 캐시가 ‘할 일 없음’으로 잘못 남는 경우를 막는 최대 지연·재조정 정책과 실행자 기동 권한을 0단계에서 검증한다. 기존 tick의 운영 가용성이 부족하면 같은 DB 실행 계약을 유지한 별도 스케줄러를 선택하고 비용·유휴 DB 접속 기준을 다시 검증한다.

기존 intel 수집용 EventBridge target의 리비전이나 명령을 정기 브리핑 개발 과정에서 임의 변경하지 않는다. 새 실행기는 실패해도 기존 수집과 수동 질의 기능을 중단시키지 않도록 분리한다.

### 7.2 작업 원장과 복구

실행 상태는 queued, waiting_sources, running, ready, published, no_change, failed, blocked_budget, canceled로 관리한다. 실제 구현에서 상태 전이표와 허용 주체를 고정한다. 보고서의 기존 done/error와 실행 상태를 혼용하지 않는다.

UNIQUE(profile_id, scheduled_for)로 동일 회차를 식별한다. 원자적 작업 선점, 만료되는 lease, heartbeat, 소유권 토큰을 사용한다. lease가 만료되어 새 실행자가 선점하면 이전 실행자는 결과를 커밋할 수 없어야 한다. 모델 응답을 저장한 뒤 프로세스가 종료된 경우 저장된 결과를 재사용한다. 응답 저장 전에 장애가 나면 모델 재호출 가능성이 있으므로 호출 시도와 비용을 기록하고 무제한 재시도를 막는다.

프로필 중지·권한 변경은 발행 및 발송 직전에 다시 확인한다. 프로필 설정 변경은 새 설정 버전을 다음 회차에 적용하고 실행 중인 회차는 기록된 버전으로 추적한다. 수신자 제거·권한 회수는 기존 스냅샷과 무관하게 즉시 적용한다.

장애 후 복구 시 놓친 회차는 기본적으로 최근 회차 한 건으로 합쳐 미반영 변화를 포함한다. 놓친 슬롯은 이력에 남기고 여러 통의 오래된 메일을 한꺼번에 보내지 않는다. 월간·3일 주기와 수동 ‘지금 생성’도 같은 기준을 적용한다. 수동 실행은 고유 요청키를 가지며 다음 정기 실행일을 바꾸지 않는다.

### 7.3 수집 지연과 불완전 자료

자료 신선도는 소스별 기대 갱신 주기로 판정한다. 월간 통계에 새 발표가 없는 것은 수집 실패가 아니다. 일일 소스의 최근 성공 여부, 최신 관측시점, 파싱 결과를 따로 표시한다.

기본 대기 한도는 생성 예정 후 30분이다. 필수 소스 장애가 남으면 기본 정책은 발행 보류와 운영자 알림이다. 사용자가 일부 자료로 발행하도록 선택한 프로필만 누락 소스를 표시한 보고서를 발행한다. 지연 자료는 다음 성공 회차에 보충하며 이미 발행된 내용의 기준시각을 바꾸지 않는다.

### 7.4 수신자별 전달

정기 보고서는 보고서 ID·수신자·채널, 중요 알림은 사건 버전·수신자·채널을 중복 방지 기준으로 삼는다. 동일 사건이 여러 프로필에 걸리면 매칭된 프로필을 부가정보로 기록한다. 발행본 확정과 전송 대기 생성은 같은 트랜잭션으로 처리한다.

전달 상태는 pending, sending, sent, failed, unknown, skipped로 구분한다. 이메일 성공·푸시 실패이면 실패 채널만 재시도한다. 자동 재시도는 동일 outbox 행에 attempts를 추가하고, 명시적 재전송은 별도 요청키와 원전송 관계를 기록한다. SES MessageId 및 채널별 결과를 반환하도록 기존 어댑터를 확장하고, 다른 알림 기능의 기존 계약은 유지한다.

외부 전송 후 응답이 유실되면 unknown으로 두고 사업자 응답·로그를 대조한다. 확인 없이 자동 재발송하여 중복을 만드는 것을 피하고, 운영자의 명시적 재전송은 이력을 남긴다. 외부 이메일의 완전한 단 한 번 전달을 보장한다고 표현하지 않는다.

## 8 권한과 비용 관리

### 8.1 권한 적용

권한은 프로필 관리, 보고서 열람, 원자료 조회, 사업장 등록, 영업 수정으로 나눈다. 기존 sales.view/sales.edit, facility.edit, contract.view, contact.view 등의 권한 이름과 실제 대상 범위는 0단계에서 대조하고 새 기능에 명시적으로 연결한다. 단순 메뉴 진입 권한만으로 내부 자료 전체를 읽지 않는다.

개인 보고서는 소유자, 공유 보고서는 명시한 수신자와 허용된 관리자만 열람한다. 새 보고서의 공통 검사 함수를 목록·검색·상세·PDF·추가 분석·공유·삭제에 적용한다. 기존 수동 보고서는 legacy_sales 범위로 명시해 기존 공용 열람 정책을 보존하되, 새 내부정보가 포함된 추가분석은 새 권한 정책의 발행본으로 생성한다.

외부 산업정보 본문과 내부 영업·계약 부록을 분리한다. 외부 본문의 요약·서비스 추천·점수·순위에는 공개 근거 평가만 사용한다. 계약 유무·담당자·내부 관계가 반영된 평가 결과도 내부 부록으로 분리한다. 외부 본문은 같은 근거로 재사용하고 내부 부록은 수신자의 현재 권한으로 조회한다. 1차 자동 메일·푸시는 외부 핵심 요약과 인증이 필요한 보고서 링크만 전송한다. 내부 계약·연락처를 자동 메일 첨부에 포함하지 않는다. 수동 PDF는 출력 시점의 권한으로 본문과 부록을 구성한다.

내부 정보를 AI로 분석하는 경로는 수신자·조회자의 권한을 적용한 후 문맥을 구성한다. 전체 자료를 AI에 보낸 뒤 화면에서만 숨기지 않는다. 보고서·PDF 캐시는 사용자 또는 동일 권한 범위를 구분하고 권한 회수 후 재사용되지 않도록 한다. 비공개 보고서 제목과 수신자 이름을 기존 전역 알림에 기록하지 않는다.

외부 문서 내용은 분석 대상 자료로 취급한다. 문서 안의 명령문으로 수신자·권한·도구 실행·영업 전환이 변경되지 않도록 고정된 처리 경로와 출력 검증을 사용한다.

### 8.2 AI 사용량과 비용

기존 AI 게이트웨이에 정기 브리핑, 문서 사실 추출, 서비스 평가의 기능 키를 등록한다. run ID 또는 문서 revision ID를 사용량 기록과 연결한다. 모델은 현재 관리 설정을 따르며 특정 모델명·가격을 계획에 고정하지 않는다.

문서가 바뀌지 않으면 재추출·재임베딩하지 않는다. 동일 공개 근거의 공통 요약은 재사용하고, 무변경 브리핑은 AI 호출을 생략한다. 실행별 입력량·출력량·재시도·동시 실행 수와 기존 월 예산 차단을 적용한다. 예산 초과는 실패 사유가 있는 blocked_budget으로 남기며 성공으로 기록하지 않는다.

초기 생성 동시 실행은 2개, 자동 재시도는 일시 오류에 최대 2회로 시작한다. 실제 처리시간과 비용을 시범운영에서 측정해 조정한다. 이용료 추정은 문서별 신규 분석량과 프로필별 생성량에 측정된 평균 비용을 적용하며, 수신자 수만큼 보고서 전체를 다시 생성하지 않는다.

## 9 단계별 작업 순서

다음 단계는 의존관계가 충족되면 병행할 수 있다. 개발 착수·인증 발급·외부 이용 허용 일정이 확정되지 않았으므로 달력상 완료일은 고정하지 않는다. 기능별 담당과 추정 소요는 0단계에서 개발 인력 기준으로 산정한다.

### 10.2 품질 표본과 목표

실제 수집·이용이 가능한 자료에서 투자 신호 100건, 복수 출처 프로젝트 묶음 30개, 서로 다른 공장을 혼동하기 쉬운 사례 20개, 신규 사업장 후보 20개를 검수용으로 선정한다. 표본은 중복될 수 있다. 지연·정정·중단·금액 미상·다중 사업 사례를 포함하고 부족한 경계 사례는 명확히 표시한 합성 자료로 보완한다.

- 제목·URL·출처·게시일 또는 날짜 미확인 표시: 표본 100% 일치.
- 투자액·통화·단위·실제 사업장·추진 단계의 명시 사실 추출: 원문에 존재하는 필드 기준 95% 이상 정확도. 원문에 없는 중요 사실의 생성은 허용하지 않음.
- 자동 프로젝트 병합: 검수 표본에서 잘못된 병합 0건. 애매한 건은 자동화 비율을 높이기보다 검토 목록으로 이동.
- 보고서 핵심 수치·인용 대상: 검수 표본 100% 대조 가능, 근거 없는 주요 주장 0건.
- 상위 추천 10건의 영업 검토 적합성: 영업 담당자 검수에서 8건 이상을 유효한 검토 대상으로 평가하는 것을 초기 목표로 설정. 수주율 목표로 해석하지 않음.
- 통계: 선정한 시계열의 단위·시점·원자료 값 100% 일치, 개정치 반영 및 증감 계산 검증.
- 정상 부하: 생성 예정 시각부터 15분 이내 발행, 확인된 중요 사건부터 15분 이내 전달을 초기 목표로 측정. 소스 지연·외부 장애는 원인과 실제 지연을 별도 기록.

숫자·권한·중복·부분 성공 방지 기준은 출시 필수다. 추천 적합성이나 처리시간이 목표에 못 미치면 원인과 조정 결과를 기록하고 재검수한다. 검증 표본·분모·오류 사례를 남겨 비율만으로 결과를 보고하지 않는다.

### 10.3 개발 검증 방식

주기 계산, 필터, 단위 정규화, 점수, 상태 전이는 단위 검증한다. 실제 PostgreSQL의 고유 제약·잠금·트랜잭션·lease는 통합 검증한다. 모델 응답은 정상·잘림·근거 오류 사례를 고정한 검증과 제한된 실제 호출 검증을 함께 수행한다. 권한·PDF·발행·영업 전환은 API 및 화면 시나리오로 확인한다.

시범 부하는 프로필 20개, 동일 시각 10개 실행, 보고서당 프로젝트 200개·근거 문서 1,000개를 시작 기준으로 삼는다. 0단계의 운영량이 이보다 크면 실제 예상치의 2배로 조정한다. 보고서 상세 목록은 페이지로 나누되 집계 모수는 잘리지 않아야 한다.

현재 저장소는 빌드 성공만으로 타입·린트 통과를 보장하지 않으므로, 변경 파일과 공통 영향 경로의 타입 검사·적절한 테스트 결과를 별도로 남긴다. 기존 오류와 이번 변경으로 추가된 오류를 구분한다.

## 11 시범운영과 배포

처음에는 기능 플래그를 비활성 상태로 배포하고 실제 발송 없이 발행 결과를 확인한다. 반도체 주간, 전자부품 일간, 특정 지역 3일 주기, 월간 경영진의 네 가지 시범 프로필을 구성한다. 월간·월말은 시간 제어 검증으로 먼저 확인하고 실제 첫 월간 회차도 운영 후 추적한다.

검수 순서는 읽기 전용 결과 확인 → 앱 수신함 → 지정 시범 사용자의 앱 알림·메일 → F06·F07 확정 동작 → 대상 사용자 확대다. 최소 7일 동안 수집·실행·중복·정정·전달 실패·비용을 관찰한다. 자료 변경이 실제로 발생하지 않은 소스는 저장된 검증 응답으로 변경 처리를 추가 확인한다.

기존 데이터 보강은 신규분부터 적용하고, 승인된 최근 자료를 제한된 묶음으로 소급 처리한다. 기존 브리핑이나 영업건을 일괄 덮어쓰지 않는다. 배포 전후 기존 수집·입찰·수동 브리핑·영업 목록의 기준 결과를 비교한다.

저장소의 [운영 지침](../CLAUDE.md)에 main 기준 배포와 Terraform 적용의 임시 중지 및 기존 스케줄 리비전 보호 조건이 남아 있다. 실제 배포 단계에서는 해당 조건의 해제 근거와 최신 배포 가드를 확인해야 한다. 이 항목은 문서 작성이나 독립 개발·검증을 막는 조건이 아니라 배포 진입 조건이다. 계획 단계에서는 운영 배포·DB 변경을 수행하지 않는다.

문제 발생 시 정기 실행과 발송을 먼저 중지하고 수동 브리핑·기존 수집은 유지한다. 선점 토큰을 무효화하여 중지된 실행자가 뒤늦게 발행하지 못하게 한다. 신규 테이블을 즉시 삭제하지 않고 결과·감사·전달 이력을 보존한다. 이미 만들어진 영업건·완료 활동은 자동 삭제하지 않고 기존 취소·정정 절차로 처리한다.
