# 사업장 마스터 정비 구현·검증 결과

작성일: 2026-09-08. 구현 위치: `codex/facility-quality` 브랜치의 로컬 작업 사본. 운영 배포·운영 마스터 수정·커밋·푸시는 수행하지 않았다.

## 제공 기능

`/facilities/missing`을 **상시 사용하는 사업장 정보 전수 점검 화면**으로 확장했다. 사업장 마스터에서 진입하여 다음 작업을 반복 실행한다. 정기 자동 실행 일정은 설정하지 않았다.

1. 전체 원본 점검: 삭제되지 않은 사업장의 다섯 필드와 보조 번호를 한 시점의 원본으로 저장하고 진단한다.
2. 외부 보완 후보 찾기: 표본 50개·100개 또는 전체, 네이버·DART·금융위원회·비즈노를 선택한다.
3. 원본 진단: 항목·상태로 필터링하고 보조 번호, 출처별 조회 결과, 확인이 필요한 사업장을 확인한다.
4. 후보 검토: 기존값·제안값·조회된 업체명·등록번호·본사/사업장 구분·출처·조회일을 비교한다. 외부 후보는 기본 미선택이다.
5. 선택 반영·제외·복원: 저장된 후보 ID만 서버로 보낸다. 같은 항목의 여러 후보를 함께 반영할 수 없다.
6. 저장된 작업 재개 및 조건별 JSON 보고서 다운로드. 브라우저를 닫아도 작업과 후보는 DB에 남는다.

편집 기능은 서버의 `facility.edit` 권한으로 제한한다. 표기 정리도 사용자가 명시적으로 선택하여 반영한다. 외부 조회 워커가 연결되지 않았다면 작업은 대기 상태로 저장하고 화면에 연결 상태를 표시한다.

사업장 신규 등록·상세 수정에도 공통 검증을 적용했다. 마스터 법인번호와 사업자등록증 추출 법인번호는 별도 입력·저장한다. 기존 업종 누락 목록과 상세 수동 수정은 `/facilities/missing/industry`에서 제공한다. **업종코드·업종명의 기존 자동 보완 흐름은 이번 다섯 필드용 엔진에 포함하지 않았다.** 기존 `{items: [{field,value,...}]}` 일반 보완 API는 교체되었으므로 구 클라이언트와 호환되지 않는다.

## 정보원과 매칭 원칙

- 네이버는 통합검색의 NICE 기반 기업정보 카드와 실제 기본정보 링크를 사용한다. Local API·플레이스·뉴스의 사람 이름을 대표자 후보로 사용하지 않는다. 화면의 한 카드 안에 표시된 허용 필드만 읽고 복수 카드·구조 변화는 확인 대상으로 처리한다.
- 대표자 검토는 네이버 카드를 우선한다. DART·금융위의 대표자 후보는 출처와 적용 범위를 함께 표시하는 보조 후보다. 조회일 및 데이터 개방일을 대표자 변경일로 표현하지 않는다.
- 비즈노는 사업자번호·법인번호·전화·주소만 읽는다. **대표자 셀은 읽지 않으며 후보 DB에도 비즈노 대표자를 넣을 수 없다.** 도로명과 지번 주소를 붙여서 하나의 주소로 저장하지 않는다.
- NICE 카드와 상세 링크의 연결 식별자를 보존한다. 별도 NICE 유료 계약이나 가려진 항목 복원은 하지 않았다. 독립 NICE 수집기는 이번 실사용 정보원에 포함하지 않았다.
- 이름의 법인 표기·공백을 정규화하고, 제한된 공장/지점 접미사 변형만 검색한다. 붙여 쓴 복잡한 공장명은 미검출로 남을 수 있다.
- 사업자번호 일치와 법인번호 일치를 구분하며, 법인이 같아도 본사 주소·전화가 해당 공장 정보인지는 별도 확인한다. 다른 식별번호는 반영 차단 사유다.
- 캡차·접근 제한·일일 한도는 정보원별로 중단한다. 한 정보원 실패가 다른 정보원 조회를 막지 않는다. 이름만 같은 프로필은 캐시 공유하지 않는다.

## 저장·재개·복원

신규 `220_facility_quality.sql`은 실행·사업장 스냅샷·후보·조회량·캐시·확정 필드 상태를 저장한다. 외부 네트워크 요청을 DB 트랜잭션 안에서 기다리지 않는다.

워커는 DB 실행 소유권과 주기적 갱신, 사업장별·정보원별 저장 지점을 사용한다. SQS 재전달 및 중복 워커는 중복 처리하지 않는다. 실패한 정보원만 재시도하고 완료된 조회는 재사용한다. 일일 한도에 걸린 작업은 이후 화면에서 재개한다. 자동 익일 재개 일정은 없다.

반영 시 사업장과 후보를 잠그고, 조회 당시 식별정보 및 대상 필드의 원본이 그대로인지 확인한다. 다른 사용자가 수정했으면 충돌로 남긴다. 주소와 정규화 주소·원문 유지 여부·지역 분류를 함께 갱신하고 추가 주소를 보존한다.

변경 전후·출처·사용자·후보 ID를 감사 이력에 기록한다. 복원은 현재값과 확정 상태가 해당 반영 직후와 같을 때만 가능하다. 이후의 수동 수정은 덮지 않는다.

정비에서 확정한 다섯 필드는 DB 트리거가 등록증 재업로드·그룹 동기화 등의 재유입으로부터 보호한다. 다른 값은 별도 충돌 후보로 남기며 등록증 원본 컬럼은 별도로 보존한다. 추출값 검토의 마스터 동기화도 실제 저장값을 확인하여 보호된 변경을 적용 성공으로 보고하지 않는다.

## 검증 범위

- 핵심 규칙·PostgreSQL 통합 테스트 5개 통과: 번호·전화 예외, 출처 충돌, 비즈노 대표자 금지, 마이그레이션 재실행, 후보 중복 방지, 여러 필드 적용, 동시 수정 충돌, 주소 복원, 재수집 보호, 중복 워커 및 실패 소스만 재개.
- 브라우저 파서 테스트 2개 통과: 네이버 카드 경계와 복수 카드, 비즈노 대표자 셀 접근 금지·주소 선택.
- API의 실제 필터 조건을 로컬 PostgreSQL에 대입한 32가지 읽기 전용 조회 통과.
- 합성 데이터의 화면 검증 통과: 선택·반영·복원, 항목 필터, 라이트/다크, 모바일 가로 넘침, 브라우저 실행 오류 없음. 이미지의 `검증회사(주)`는 테스트용 데이터다. 운영 로그인과 AWS 워커를 연결한 전체 경로 시험은 배포 후 필요하다.
- Next 프로덕션 빌드 통과. 프로젝트 설정상 빌드는 기존 타입 오류를 무시하므로 별도 타입 검사를 실시했다. 프론트는 기존 기준 대비 새 진단이 없고, 스크래퍼 검사에서도 신규 정비 파일의 진단은 없었다. 프로젝트 전체 타입 검사에 남은 기존 오류가 있으므로 전체 타입 검사 통과라고 표현하지 않는다.

## 배포 순서와 설정

배포 준비 중 운영 환경에 SQS 워커 실행기가 없음을 확인하여, 외부 조회 요청 시 `RunTask`로 워커를 기동하도록 연결을 추가했다. 워커는 `--drain`으로 대기 큐를 처리하고 종료한다. `facility-quality-worker.tf`는 해당 클러스터·워커 정의와 기존 태스크 역할만 허용하는 실행 권한이다. 프론트에는 `MCM_FACILITY_QUALITY_TASK_DEFINITION`, `MCM_FACILITY_QUALITY_CLUSTER`, `MCM_FACILITY_QUALITY_SUBNETS`, `MCM_FACILITY_QUALITY_SECURITY_GROUPS`도 필요하다. 배포 스크립트의 `-FacilityQualityEnvironmentFile`은 이 설정과 준비 플래그만 받는다. 실제 컨테이너의 Playwright 버전도 잠금 파일의 1.59.1과 일치시켰다.

아래는 아직 실행하지 않은 배포 절차다. 저장소의 배포 가드를 따라 별도로 진행한다.

1. 배포 직전 원격 브랜치를 다시 확인하고 신규 마이그레이션 번호 충돌 여부를 확인한다. `infra/aws/ops/staging-apply-migrations.ps1 -Files 220_facility_quality.sql`을 이용한다. 이미 적용한 마이그레이션을 수정하거나 번호를 재사용하지 않는다.
2. 새 워커 이미지를 빌드하고 현재 태스크 정의의 설정을 보존하여 새 리비전을 등록한다. `PGHOST`, `PGPORT`, `PGDATABASE`, Secret 참조의 `PGUSER`, `PGPASSWORD`, 기존 `DART_API_KEY`, `DATA_GO_KR_API_KEY`가 필요하다. 기존 고정 IP DART 프록시 설정도 보존한다. DB 네트워크와 인증, 네이버·비즈노 브라우저 실행을 확인한다.
3. `infra/aws/ecs.tf`의 워커 환경 및 Secret 참조를 갱신했다. 다만 현재 리소스는 `ignore_changes = [container_definitions]`를 사용하므로 Terraform 파일 변경만으로 실행 중 태스크 정의에 반영되지 않는다. SQS 실행기가 새 워커 태스크 리비전을 사용하도록 등록 상태도 확인한다.
4. 프론트는 반드시 `infra/aws/ops/staging-deploy-next.ps1`의 브랜치 누락 검사와 배포 절차를 사용한다. 가드를 강제로 무시하지 않는다.
5. 새 작업 유형을 처리하는 워커가 준비된 뒤 프론트의 `MCM_FACILITY_QUALITY_WORKER_READY=true`를 켠다. `MCM_JOB_QUEUE_MODE=sqs`와 기존 큐 URL도 필요하다. 준비 플래그가 없으면 작업 저장만 하고 구 워커에 전달하지 않는다.
6. 배포 후 실제 권한·작업 전달·소규모 후보 생성·검토 화면을 점검한다. 운영 마스터 반영은 출처를 검토한 후보를 선택하는 별도 작업이다. 이번 로컬 표본을 운영에 자동 복사하지 않는다.

기본 조회 제한: 비즈노 일일 100회, 나머지 정보원 각각 600회. 브라우저 탐색 간격 3초이며 최소 1.5초다. 사업장 수가 아니라 실제 요청/탐색 횟수 기준이다. `FACILITY_QUALITY_<SOURCE>_DAILY_LIMIT`과 `FACILITY_QUALITY_INTERVAL_MS`로 조정하며 소스 이름은 `NAVER`, `BIZNO`, `DART`, `FSC`다. 동일 식별번호 프로필 캐시는 24시간이다.

CLI는 `scraper/scripts/cli-facility-quality.ts --audit` 또는 `--run=<저장된 작업 ID>`로 사용할 수 있다. 로컬 파일럿 CLI는 localhost의 지정 검증 DB만 허용한다. 인증 값은 환경 변수로 공급하고 문서나 소스에 넣지 않는다.
