# 공문 발송 관리 시스템 블루프린트 (초안 v1 — 확인 대기)

작성 2026-07-21. 샘플 실측: 발신 공문 4건(기성 청구·독촉·준공계·계약 변경) + 공문 기본 템플릿 1건.
확정 전 문서 — §9 미결 논점에 대한 사용자 확인 후 구현 계획을 확정한다.

## 1. 배경 / 문제

현행 공문 발송 프로세스의 문제:
1. **수동 채번**: 담당자가 관리자(사용자)에게 공문번호를 문의해 받아야 함 — 병목·기록 분산.
2. **발송본 회수 누락 빈발**: 발송 후 관리자에게 공문 사본을 전달해야 하나 누락이 잦아
   공문 대장이 불완전해짐.
3. **내부결재 부재**: 작성자가 곧바로 발송 — 검토·승인 단계가 없어 품질/책임 리스크.

## 2. 목표

MCM 앱에 공문 발송 기능을 탑재해 **작성 → 내부결재 → 채번 → 문서 생성(HWPX) →
발송 기록 → 보관**을 일원화한다. 작성 시점에 시스템에 기록되므로 회수 누락이 원천 차단된다.

## 3. 현행 실측 (샘플 분석)

### 3-1. 공문번호 체계
`{YYYY}-대외-{NNNNN}` (예: 2026-대외-01019). 연도별 일련 순차 증가
(01009=3월 → 01019=5월 → 01032=7월). 파일 보관은
`발신 공문/{연도}/({공문번호}){제목}/` 폴더에 hwp+pdf+첨부 동봉.

### 3-2. 문서 구조 (공통 골격)
- **상단(고정)**: 회사명 국/영문 로고부 → `수신` / `참조` / `제목`
  - **내용증명 변형**(독촉 3회차~): 수신/참조 대신 `발신`(자사 주소+사업자번호+대표) /
    `수신`(상대 주소+사업자번호+대표) 풀 포맷 — 내용증명 요건.
- **본문(가변)**: `1. 인사말` → `2. 취지 문단`(계약일+「용역명」 인용) → [내역 표] →
  `붙임 : 1. … 1부` 목록. ※유형·상대별로 자유 — **표준화 대상 아님**(간단 템플릿만 제공).
- **하단(고정)**: `주식회사 한국환경안전연구원 대표이사 이유억`(직인부) →
  `담당 : {이름} {직급}` + `대표이사 : 이유억` → `시행 : {공문번호} ({YYYY. MM. DD.})` →
  `전화 : 02-6672-0035 / kaikan00@naver.com`.

### 3-3. 유형 7종 × 데이터 연동 매트릭스

| # | 유형 | 빈도 | 계약 연동 | 자동 주입 후보 | 첨부(표준화 생성 대상) |
|---|---|---|---|---|---|
| 1 | 기성금 청구 | 높음 | 계약+기성 단계 | 취지문(계약일·용역명), 기성 내역 표(단계 금액) | **대금청구서**, (기성내역서=발주처별 상이 → 제외) |
| 2 | 착수계 송부 | 높음 | 계약 | 취지문, 착수 정보 | **착수계**, 용역 공정표(공정표는 contract_process_stages 연동 후보) |
| 3 | 용역 변경 요청 | 중 | 계약 | 취지문, 변경 대비 표(기존↔변경) | 없는 경우 多 |
| 4 | 준공계 제출 | 높음 | 계약+준공 단계 | 취지문, 준공 정보 | **준공계**, **대금청구서**, (준공내역서=제외) |
| 5 | 요청 회신 | 중 | 선택 | 원 요청 참조 문구 | 자유 업로드 |
| 6 | 미지급금 독촉 | 높음 | 계약+미수 단계 | **미수금 표 자동**(발행됐으나 미수금 단계: invoice_issued=1 & payment_collected=0), 지급기한 | **대금청구서**, 세금계산서(발행분 업로드) |
| 7 | 견적서 발송 | 낮음 | 선택 | 취지문 | 견적서(업로드) |

- 독촉은 **회차 관리**: 1~2회 일반 발송, 이후 **내용증명 모드**(§3-2 변형 상단) 전환.
- 계약 연동 데이터 소스(기존 테이블): `contracts`(계약일·용역명·금액),
  `contract_payment_milestones`(stage_label/amount/invoice_issued(_at)/invoice_amount/
  payment_collected/collected_amount — 기성·미수·준공 전부 커버), `facilities`+
  `facility_contact_people`(수신처·참조 담당자), `company_profile`(자사 정보·대표자).

## 4. 핵심 설계

### 4-1. 공문대장 + 자동 채번
- 공문 생성 시 시스템이 `{연도}-대외-{일련}` 자동 채번(연도별 시퀀스, DB 원자적 증가).
- 공문대장 화면 = 번호/유형/수신처/제목/담당/상태/시행일/발송 채널 목록 + 검색.
- 채번 시점·결번 정책은 §9 논점(현행 관행은 "작성 전 번호 부여" = 기안 시 선점 채번).

### 4-2. 본문 편집 — 한글 구동 없이 앱에서 편집 (★가능)
**결론: 가능하다.** 완전한 아래아한글 WYSIWYG 은 아니지만, 공문 본문의 실제 구성요소가
"번호 문단·내역 표·붙임 목록" 3종이므로 **구조화 블록 에디터 + 서버 HWPX 조립**로 충분히 커버된다.

- **방식 A(채택 제안) — 구조화 본문 블록 + 서버 주입**:
  본문을 블록 시퀀스로 모델링: `번호 문단`(1., 2., … 자동 넘버링, 자유 텍스트) /
  `표 블록`(열 정의+행 그리드 입력, 단위 표기·합계 행 옵션) / `붙임 목록`(항목+부수).
  서버가 기본 템플릿 HWPX 의 본문 슬롯에 문단·표를 조립 주입.
  - **실증 근거**: 입찰 P3 에서 셀 텍스트 치환·문단 복제·표 행 복제(rowAddr/rowCnt 재계산)·
    linesegarray 제거·pageBreak 제어 전부 구현·검증됨(`lib/bid/hwpx-fill.ts`).
    업무보고의 행 단위 구조화 입력기(`StructuredNoteEditor`, 소제목/글머리 자동넘버링) 계보의
    에디터 UI 를 공문 블록용으로 확장.
  - **한계**: 자유 서식(부분 글자색·개체 삽입·복잡 셀병합)은 미지원. 필요 시 생성된 HWPX 를
    한글에서 열어 미세 수정 → 최종본 업로드로 교체(대장·보관은 유지).
- 방식 B(비채택) — 웹 리치텍스트(TipTap 등)→HWPX 변환: 자유도는 높으나 변환 매핑이 방대하고
  신규 라이브러리 도입 부담. 공문 용도에 과함.
- 방식 C(배제) — 한컴 웹오피스 SDK: 상용 라이선스·별도 서버 필요.
- PDF 는 입찰 P3 확정 방식과 동일: **생성 HWPX 를 사용자가 한글에서 PDF 변환**(발송용).

### 4-3. 기본 템플릿 슬롯화
`공문 기본 템플릿.hwp` → **HWPX 로 저장한 사본 필요(P0, 사용자)** → 슬롯 분석:
수신/참조/제목/본문 영역/붙임/담당(이름·직급)/시행 번호·일자. 상단 로고부·하단 직인부는
템플릿 원본 그대로 보존(치환하지 않음). 내용증명 변형은 상단 블록 교체(자사 정보는
`company_profile` 에서, 상대 정보는 수신처 데이터에서).
- 템플릿 관리: 발주처별이 아니라 **전사 1벌(+내용증명 변형)** — 입찰 양식 라이브러리보다 단순.
  단, 템플릿 교체 업로드 가능하게(로고·직인 변경 대비).

### 4-4. 내부결재 — 전자결재 코어 위임 (2026-07-21 방침 변경)
- **방침 변경**: "전자결재 보류" 결정이 철회되고 MCM 에 전자결재를 정식 탑재하기로 함
  (`docs/e-approval-blueprint.md`). 공문의 내부결재는 초안의 "경량 승인" 대신
  **전자결재 코어의 결재 플로우를 그대로 사용**한다 — 공문 기안 = 전자결재의 한 양식군,
  결재 완료 시 공문 채번·HWPX 생성·발송 기록으로 이어지는 도메인 확장.
- 공문 상태 머신은 전자결재 문서 상태에 발송 단계를 얹은 형태:
  `draft` → `in_progress`(상신) → `approved`/`rejected` → `sent`(발송 기록). +`voided`(결번).
- 채번기(`doc_no_sequences`)·문서함(공문 발송함)·알림도 전자결재 코어와 공유.
- 구축 선후는 전자결재 블루프린트 §8-2 논점(권고: 전자결재 코어 먼저 → 공문 첫 탑재).

### 4-5. 첨부서류 생성 — 입찰 P2 양식 분석/매핑 재사용
- 대상: **착수계·준공계·대금청구서**(+공정표는 후보). 기성/준공내역서는 발주처별 포맷
  상이로 **제외(확정)**.
- 방식: 입찰 서류 생성에서 실증한 **양식 업로드 → LLM 셀 매핑(form_profile) → 데이터 주입**
  파이프라인(`hwpx-form.ts`/`form-analyze.ts`/`hwpx-fill.ts`)을 공문 첨부용 문서 카탈로그로
  확장. 주입 데이터 = 계약·기성 단계·회사 프로필(입찰 package-values 리졸버 패턴).
- **양식 파일은 사용자가 추후 업로드 예정** → 수령 후 카탈로그(문서 타입×필드 수퍼셋) 확정.
- 외부 작성 첨부(4대보험 완납증명서·세금계산서 등)는 항상 업로드 첨부 가능.

### 4-6. 보관·발송 기록
- S3 `letters/{연도}/{공문번호}/` 에 생성 HWPX + 업로드 첨부 + (발송 PDF 업로드) 보관 —
  현행 V: 드라이브 폴더 구조와 동형. 공문대장에서 일괄 다운로드(zip).
- 발송 기록: 채널(이메일/우편/내용증명/팩스/직접전달), 발송일, 발송자, 비고.
  발송 완료 입력 시 상태 `sent`.

## 5. 데이터 모델 초안 (084~, 관례: text 타임스탬프·integer boolean·멱등)

- `official_letter_sequences(year text PK, last_seq integer)` — 연도별 채번(원자적 UPDATE).
- `official_letters(letter_id PK, letter_no UNIQUE, year, seq, letter_type(7종+기타),
  status, title, body jsonb(블록 모델), recipient_org, recipient_contact(참조),
  recipient_detail jsonb(내용증명용 주소·사업자번호·대표), is_content_proof integer,
  dunning_round integer(독촉 회차), contract_id FK?, milestone_ids jsonb,
  drafted_by(employee/user), send_channel, sent_at, sent_by, output_key(생성 HWPX),
  final_key(최종본 교체 업로드), created_at, updated_at)`.
- `official_letter_attachments(attachment_id PK, letter_id FK, kind(generated|uploaded),
  doc_type(대금청구서/착수계/준공계/기타), display_name, storage_key, byte_size, sort_order)`.
- `official_letter_approvals(approval_id PK, letter_id FK, step, approver_user_id, action
  (submit|approve|reject|void), comment, acted_at)` — 전건 이력.
- `official_letter_templates(template_id PK, kind(base|content_proof), storage_key,
  form_profile jsonb(슬롯 매핑), updated_at)` — 전사 템플릿 1+1벌.
- 첨부서류 양식: 입찰 `bid_package_forms` 와 별개로 `letter_doc_forms`(doc_type 당 1벌,
  form_profile jsonb) — P2 분석 파이프라인 공유(양식 수령 후 확정).

## 6. 화면 구성 (cdash)

1. **공문 대장**(메인 목록): 연도 탭+유형/상태 필터+검색, 행=번호·유형·수신처·제목·담당·
   상태 배지·시행일. 행 클릭 → 상세(파일·결재 이력·발송 기록).
2. **공문 작성**: ①유형 선택 → ②계약 연동(유형별: 계약 검색·기성/미수 단계 선택 →
   취지문·표 초안 자동 생성) → ③수신처(거래처 담당자 연동+수기) → ④본문 블록 에디터
   → ⑤첨부(생성/업로드) → 저장(draft)·결재 요청.
3. **결재함**: 승인자용 대기 목록 + 문서 미리보기(본문 블록 렌더) + 승인/반려(사유).
4. **발송 처리**: 승인 건 다운로드(HWPX/zip) → 발송 후 채널·일자 기록(+최종본 PDF 업로드).
- 사이드바 위치·진입점은 §9 논점.

## 7. 구현 단계 (안)

1. **P0 준비**: 기본 템플릿 HWPX 수령·슬롯 분석 / 첨부서류 양식(착수계·준공계·대금청구서)
   수령·카탈로그 확정 / §9 논점 확정 → 구현 계획 최종화.
2. **P1 공문대장·작성·생성**: 084 스키마 + 자동 채번 + 작성 화면(유형·수신처·본문 블록
   에디터 1차) + 템플릿 HWPX 조립 생성 + S3 보관.
3. **P2 결재·발송**: 승인 플로우(요청→승인/반려) + 결재함 + 발송 기록 + 대장 완성.
4. **P3 유형 자동화**: 계약·기성/미수 단계 연동 자동 주입(취지문·내역 표·미수금 표) +
   독촉 회차·내용증명 모드.
5. **P4 첨부서류 생성**: letter_doc_forms + P2 매핑 재사용 주입(양식 업로드 후).

## 9. 미결 논점 (사용자 확인 필요)

1. **채번 시점·결번 정책**: (a) 기안 시 즉시 채번(현행 관행 유사 — 반려·폐기 시 결번 발생,
   voided 로 대장에 남김) vs (b) 결재 승인 시 채번(결번 없음 — 단 작성 중 번호 미확정).
2. **일련번호 규칙**: 01000 부터 시작하는 이유(01001 시작? 임의 오프셋?). 연도 리셋 확인.
   '대외' 외 구분(내부 공문 등) 존재 여부 — 시스템 범위에 포함할지.
3. **결재선**: 단일 승인자(대표이사)로 충분한가, 부서장 검토 → 대표 승인 2단인가.
   대표 부재 시 대결(위임) 필요 여부.
4. **직인**: 생성 HWPX 에 직인 이미지까지 포함(템플릿에 내장돼 있으면 그대로 보존됨) vs
   발송 직전 날인. 템플릿 HWPX 수령 시 확인.
5. **과거 공문 소급 등록**: V: 드라이브 기존 발신 공문 대장을 백필할지(폴더명 패턴 파싱으로
   자동 수집 가능), 아니면 신규 건부터 시작할지.
6. **메뉴 위치**: 영업(sales) 산하 vs 별도 '문서/공문' 섹션. 진입 권한(전 직원 작성 가능?).
7. **발송 채널**: 이메일 발송을 시스템에서 직접(SES — 스크래퍼 알림 인프라 존치) 할지,
   기록만 할지(1차는 기록만 제안).
8. **수신처 마스터**: 발주처·거래처 연락처를 `facility_contact_people` 재사용으로 충분한가,
   공문 전용 수신처 관리(비사업장 상대: 유관 업체·기관)가 필요한가.
