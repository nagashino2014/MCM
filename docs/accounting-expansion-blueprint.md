## ★ 설계 대원칙 — 아마란스10 도입 실패의 교훈 (사용자 지시, 2026-08-16)

**우리 회사는 아마란스10을 실제 도입하고도 사내 이용에 실패했다.** 원인(사용자 증언):
- 기능은 매우 다양하고 많으나 **메뉴가 쓸데없이 복잡**하고, 불필요해 보이는 상세 설정이 과다.
- 프로그램이 기본적으로 **무겁고 오류가 잦아** 관리자 입장에서도 불편.
- 복잡하고 어려운 메뉴 탓에 **직원들에게 사용을 유도하기 난해**.

따라서 §3의 메뉴 트리(약 230개 화면)는 **따라잡을 목표가 아니라 반면교사**다. 이 문서의 모든 기능 설계는 아래 원칙을 우선한다:

| # | 원칙 | 적용 방식 |
|---|---|---|
| U1 | **일반 사용자 화면은 "지독한 컴맹"도 즉시 조작 가능해야 한다** — 기능의 다양함보다 우선 | 직원이 만지는 플로우는 3탭 이내(촬영→확인→저장, 선택→목적 입력→상신). 설정·규칙·매핑은 직원 화면에서 완전히 배제 |
| U2 | **복잡성은 관리자 뒤편으로 격리 (progressive disclosure)** | 전표·분류 규칙·계정과목 같은 회계 개념은 `finance.*` 권한자 전용 화면에만. 직원은 회계 용어를 몰라도 됨(계정과목 선택조차 자동분류가 대신) |
| U3 | **설정보다 자동화·스마트 기본값** | 아마란스식 "용도설정/양식별연결/취합자설정" 같은 사전 설정 화면을 만들지 않는다. 학습 사전·규칙이 사용 중에 자동으로 쌓이는 현행 방식(card_merchant_links) 유지 |
| U4 | **메뉴를 늘리지 않는다** | 신규 기능은 기존 진입점(기안 화면·재무 보드 탭·모바일 홈 타일)에 흡수. 사이드바 메뉴 추가는 최후 수단 |
| U5 | **가볍고 오류 없는 것이 기능보다 중요** | 화면당 초기 로드 최소화(페이징·지연 로드), 실패 시 사용자 언어로 안내(전문용어 에러 금지), 자동 저장·재시도 |

## 2. 개인카드 영수증 촬영 스톡 (P1)

> **구현 상태(2026-08-17): 코드 완료.** 마이그 **177** + `lib/finance/{receipt-parser,receipt-pdf,receipts}.ts` + `/api/receipts*` 4라우트 + `ReceiptPickerModal` + `ApprovalDraftBoard` 연동(상신 귀속·PDF 자동 첨부) + 모바일 `receipt.tsx`(홈 타일·더보기) + 웹 셸 `/m/receipt`.
> (경위: 최초 구현은 다른 PC 세션에서 마이그 174로 작성됐으나, 본 저장소에 174~176이 이미 존재해 **177로 재번호**하여 최신 코드 기준으로 재적용함.)
> 남은 것: **마이그 177 DB 적용 · 실기기/실데이터 검증 · 배포(next 이미지 + EAS OTA)**.

### 2.1 요구 확정
- 자동 수집이 안 되는 **개인카드 지출**: 사용자가 받은 **지류 영수증을 그때그때 촬영**해 내역을 스톡.
- 파싱뿐 아니라 **영수증 이미지를 PDF화하여 S3 보존**(증빙 원본 보관).
- 지출결의서·출장보고서 작성 시 **본인 스톡에서 선택 → 표 자동 기입 → 목적만 입력**(법인카드 F1/F2와 동일 UX).
- **환급 정산 = 급여 합산 금지, 별도 이체(사용자 확정 2026-08-16)** — 급여 합산 시 급여성 지급으로 간주되어 소득세·지방소득세 증가(과거 실증). 이체 실행은 수동, P7에서 출금 대조만.

### 2.2 아키텍처 — 명함 파이프라인 복제 + 카드피커 패턴 재사용
```
[촬영] 모바일 receipt.tsx(card.tsx 패턴) · 웹 /m/receipt
   │  multipart(file)
   ▼
[파싱] POST /api/receipts/parse — business-card-parser.ts 패턴
   │  sharp 정규화 → Claude vision(Haiku) → 구조화 JSON (저장 없음, 프리필 전용)
   ▼
[확인·저장] POST /api/receipts — 사용자가 파싱 결과 확인/수정 후 저장
   │  ① 정규화 JPEG → 스토리지  ② pdf-lib 이미지 임베드 PDF → 스토리지  ③ personal_receipts INSERT
   │  중복 의심(승인번호 일치 또는 ±1일 동일 금액) 시 409 → 사용자 확인 후 force 재요청
   ▼
[불러오기] 기안 화면 ReceiptPickerModal(CardPickerModal 형제) → 표 자동 기입(_receiptId 메타)
   │  + 증빙 PDF 를 field_values.file_attachments 에 자동 추가(결재자 원본 확인)
   ▼
[상신] syncDocReceiptLinks — doc_id 귀속(본인 영수증만)·분류 확정·학습 / 반려·삭제 시 해제
```

### 2.3 파서 (`frontend/lib/finance/receipt-parser.ts`)
- 모델 `RECEIPT_PARSE_MODEL || claude-haiku-4-5`. sharp 정규화(EXIF 회전·장변 1600px) 재사용.
- 추출: 상호·사업자번호·거래일시·합계·공급가액/부가세·카드 끝4·승인번호·품목(상위 3).
- 결정론 보정: 사업자번호 10자리 검증, 금액 정합(공급가액+부가세=합계 ±1원, 어긋나면 총액-세액/총액÷11 역산 — 카드 원장과 동일 규칙).
- 자동분류: 기존 4단 분류기(`classify.ts`) 재사용 — **법인카드와 동일 계정과목 체계 공유**, 확정 시 `card_merchant_links` 학습.

### 2.4 PDF화 (`frontend/lib/finance/receipt-pdf.ts`)
- `pdf-lib` + `public/fonts/malgun.ttf`(payroll PDF 관례)로 A4 1페이지 임베드 + 하단 메타 스탬프(상호·일시·금액·촬영자·촬영일시).
- 스토리지 = `putContractDocument`(`receipts/{YYYYMM}/{id}_영수증_{상호}.{jpg,pdf}`) — **결재 첨부 뷰어와 같은 스토리지라 PDF key를 `file_attachments`에 그대로 실어 결재자가 바로 열람**.

### 2.5 데이터 모델 — 마이그 `177_personal_receipts.sql`
`personal_receipts`: `receipt_id` PK, `owner_user_id`(본인만 조회·사용), `paid_at`, `store_name`, `store_corp_num`, `total_amount`, `supply_amount`, `tax_amount`, `card_last4`, `approval_num`, `items_json`, `parsed_json`(LLM 원본), `category_key`/`category_source`, `image_key`, `pdf_key`, `doc_id`/`doc_form_id`(귀속 — card_transactions 규약), `excluded`, `memo`, `created_at`, `updated_at`.
- RBAC: 별도 권한키 없음 — `approval.view` + 본인 소유 강제. 관리 열람은 `finance.view`.

### 2.6 UI (★U1: 직원 플로우 = "찍고 → 확인하고 → 저장" / "불러와서 → 목적 쓰고 → 상신" 뿐)
1. **모바일 촬영**(`apps/mobile/src/app/receipt.tsx`): card.tsx의 카메라 오버레이·상태머신 복제. 파싱이 다 채워주므로 틀린 곳만 수정. 계정과목 등 회계 용어 비노출. "다음 영수증" 연속 촬영. 홈 빠른 실행 타일 + 더보기. 웹 셸 `/m/receipt` 동일.
2. **ReceiptPickerModal**: 기안 화면 지출 표 상단 "개인카드 영수증 불러오기"(법인카드 버튼 옆). 본인·미귀속·미제외 건 + 썸네일(클릭 확대). 다중 선택 → 표 기입 + PDF 자동 첨부.
3. **상신 훅**: `collectReceiptRefs/syncDocReceiptLinks/unlinkDocReceipts`(classify.ts 형제) — approval docs 라우트에 카드 훅과 나란히 연결.
4. 부가세 연계(후순위): 개인카드 경비는 매입세액공제 대상 아님 — vat 보드 합산 제외, "개인카드 경비" 별도 시트로 xlsx 동봉 검토.

### 아마란스 회계의 구조적 골격 (갭 분석의 기준)
1. **모든 길은 전표로**: 통장·카드·세금계산서·현금영수증·지출결의가 전부 "검증 → 자동분개 → 전표발행"으로 수렴. 장부(분개장~총계정원장)와 재무제표·부가세 서식은 전표에서 파생.
2. **지출결의 = 회계의 입구**: 결재 종결 문서를 회계 담당자가 전표로 승격. MCM의 `doc_id` 귀속과 대응되나, MCM은 "귀속"에서 멈추고 분개가 없음.
3. **관리회계 축 = 회계단위·부서·프로젝트**: 모든 재무제표가 부서별/프로젝트별로 절단 가능.
4. **경비 통제**: 동일가맹점중복사용·제한시간사용 등 감사성 리포트가 별도 분류로 존재.

## 4. 갭 분석 — MCM vs 아마란스10 (v1.3 정정판)

| # | 영역 | 아마란스10 | MCM 현재 | 갭 판정 |
|---|---|---|---|---|
| G1 | 증빙 수집(통장·카드) | CMS 연동 + 자동분개 | 바로빌 원장 수집(분개 없음) | **원장까지는 동등**, 분개 없음 |
| G2 | 지출결의→회계 반영 | 결재종결→분개생성→전표발행 | doc_id 귀속·계정과목 확정에서 종료 | **전표 계층 부재** ★핵심 |
| G3 | 전표/장부(분개장·총계정원장·시산표) | 완비 | 없음 | **부재** ★핵심 |
| G4 | 재무제표(손익·재무상태표·현금흐름) | 완비 + 부서/프로젝트별 관리용 | 없음 | **부재** — 단, 계약별 수금·매출 데이터는 이미 강함 |
| G5 | 자금관리(수지계획·자금일보·현황) | 완비 + 결재 연동 | 없음(계좌 원장만) | **부재** — 원장 데이터가 있어 착수 용이 |
| G6 | 부가세 | 신고서·매입매출장·합계표·전자신고 | 분기 집계 + xlsx | **신고 서식 부재**(집계는 있음) |
| G7 | 채권관리 | 채권연령분석·잔액조회서 | 미수금 현황 + 장기미수 + 조치이력(내용증명·추심) + 자동대조 | **부분 우위** — 연령분석 리포트만 갭 |
| G8 | 고정자산/감가상각 | 등록·상각·명세서 | 없음 | 부재 |

| G10 | 법인세 보조(접대비명세서 등) | 서식 완비 | 없음 | 부재 — 내재화 목표에 따라 P9 범위 |
| G11 | 예산관리 | 상위 소개자료에 있음(본 인스턴스 미노출) | 없음 | 부재 |
| G12 | 업무용승용차 운행기록부 | 있음 | 차량 예약 자산(`reservable_assets`)만 | 부재 — 예약+출장보고 데이터로 초안 자동화 가능(차별화 기회) |
| G13 | 급여↔회계 | 급여결재·자동분개 | 급여 모듈 별도(연계 없음) | 연계 부재 |
| G14 | 세금계산서 발행·수취 | WEHAGO 연동 | **구현 완료**(P4 발행 + P5 수정세금계산서, `tax-invoice.ts`·`invoicing.ts`) — 매입 계산서 **수집**은 미구현 | 발행은 동등 — **매입 수집만 갭**(P5 로드맵에 포함) |
| G15 | 카드→지출결의 자동화 | 카드사용내역이관(담당자 이관형) | CardPicker(4단 자동분류 + 학습) | **MCM 우위** |
| G16 | 영수증(개인카드) OCR | 없음(수기) | **P1 구현 완료**(§2) | **MCM 우위 — 차별화 완성** |

**요약**: MCM은 "증빙 수집→결재 문서화→세금계산서 발행→수금 대조"까지 아마란스와 동등 이상(자동분류·학습·영수증 OCR·미수 조치 이력은 우위)이나, **"결재 이후 → 회계장부"로 넘어가는 전표 계층(G2·G3)과 그 위의 재무제표·자금·부가세 신고(G4·G5·G6)가 없다.**

**단, 갭을 메우는 방식은 아마란스와 정반대여야 한다(★설계 대원칙).** 아마란스는 이 기능들을 230개 화면·수십 개 설정으로 풀었고 그 복잡성이 도입 실패의 직접 원인이었다. MCM은 같은 회계 실질(전표·재무제표·자금)을 **직원 노출 0, 관리자 화면 최소, 자동 생성 우선**으로 담는다 — 직원이 보는 것은 지금처럼 "기안 화면에서 불러오기 → 목적 입력 → 상신"이 전부이고, 전표·장부·리포트는 그 뒤에서 자동으로 파생되는 구조.
