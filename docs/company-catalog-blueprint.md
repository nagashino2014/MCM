## 2. SR 디자인 시스템과 회사소개서의 차이 — 무엇을 계승하고 무엇을 새로 만드는가 ★

두 문서는 "A4 지면에 정보를 신뢰 있게 담는다"는 기반은 같지만 **목적·독자·브랜드·구조가 다르다.** 그래서 SR 시스템을 그대로 쓰지 않고
**파생(fork)한 별도 시스템 「KESI 회사소개서 디자인 시스템」**을 만든다. 기초 규칙은 계승하고, 브랜드·글자 위계·쪽 유형·인포그래픽은 새로 정한다.

| 관점 | SR(지속가능경영보고서) | 회사소개서 | 처리 |
|---|---|---|---|
| 목적 | 공시·검증 — 정확성·추적성·기준 대응 | 영업·신뢰 형성 — 첫인상, 역량 증명, 기억에 남기기 | 콘텐츠 원칙 재작성 |
| 독자·읽는 방식 | 평가기관·투자자, 정독·검색 | 발주처 담당자·PQ 심사위원, **3분 훑기 → 관심 분야만 깊게 → 부록 조회** | 쪽당 메시지 1개, 큰 숫자·인포그래픽 우선 |
| 브랜드 | 발주처 브랜드 자리(중립), 색상 컨셉 4종 | **KESI 자사 브랜드 고정**(CI 그린·블루) | `brand` 계열 KESI 값으로 고정, 컨셉은 KESI 안에서 2–3종 |
| 영역 색 | E/S/G 3색(영역 의미 전용) | **사업 분야 색 5종 = 계약 관리 5분류**(통합환경허가·장외·화관법·HAPs·ESG·탄소중립·기타 용역 — D11 확정) | `env/soc/gov` → `area-1..5`로 일반화, 같은 규칙(영역 의미일 때만) |
| 구조 | 장→절→이슈→4축(고정 문구) | 회사→사업→역량→사람→신뢰 근거→연락처 / 부록 | 쪽 유형 목록 신규(§3) |
| 쪽 머리 | NavHeader 장 탭·절 탭(링크의 77–92%) | 가벼운 섹션 라벨 + 쪽 번호(탭 내비 불필요, 쪽 수 적음) | 컴포넌트 축소판 `SectionHeader` |
| 글자 위계 | 본문 9.5pt, 표 8pt, 제목 19pt | **본문 10.5–11pt, 디스플레이 36–56pt, KPI 숫자 32–48pt**(화면 발표·출력 겸용) | 타입 스케일 재정의, 부록 표만 8–8.5pt |
| 서체 | `report`·`figure` 묶음 고정(발주처 전용서체면 값만 교체) | **서체 세트를 골라 바꾸고, 새 서체를 올려 쓸 수 있어야 함** | 역할별 서체 변수(제목·본문·숫자) + 서체 라이브러리(§5) |
| 사진 | 7개 배치 형식, 사진 비중 낮음 | 사진 비중 높음(표지·간지·사업 분야 히어로), **인물 그리드** 필요 | 7개 형식 계승 + `PeopleGrid`·`LogoWall`·`CredentialGallery` 신규 |
| 도식 | 조직도·절차도 위주, 차트 적음 | **사업 분야 인포그래픽 중심**(허브·흐름·순환·지도·숫자) | **인포그래픽 라이브러리 신규(§4)** |
| 표 | 세로선 없음, 머리 `panel`, 합계 행 위, 각주 | 같은 규칙 → 부록 실적표에 그대로 | **계승** |
| 숫자 표기 | 천 단위 쉼표, 단위 한 칸, '2023 X → 2024 Y', 결측 기호 구분 | 같음 | **계승** |
| 문체 | '~습니다', 근거 없는 최상급 금지, **개인 이름 금지** | '~습니다' 계승, 최상급 대신 수치('업계 최고' → '1,307개소 중 99개소 최초허가'), **임원·인력 실명 필요** | 실명판/마스킹판 옵션(§6-6) |
| 링크·북마크 | PDF 북마크 3단, 쪽 번호 링크 필수 | 북마크 2단(섹션→쪽), 목차·부록 링크 | **계승**(Chromium `outline`·`tagged`) |
| 판형 | A4 가로 842×595pt, 화면 우선 단면 | 화면 발표·메일 첨부·출력 겸용 | **A4 가로 확정**(D1, 10-21 — 현행도 가로, SR 그리드·표 규칙 재사용, 부록 넓은 표 유리) |
| 그리드 | 2단(361pt) 고정 | 다양한 구성 필요(카드 3·4열, 비대칭 히어로) | **12열 그리드**(746pt, 거터 24) — 2단은 6+6. 캔버스 맞춤(snap) 기준 |
| 밀도 | 쪽 꽉 채움, 표 많음 | 여백 넉넉(본편), 부록만 고밀도 | 본편/부록 밀도 규칙 분리 |

**계승하는 기반**(복사 후 이름만 일반화): `ink`·`rule`·`status`·`overlay`·`photo-*` 색, 간격 단위(4/8/12/16/24/32), 반경(0/3/999),
선 굵기(0.25/1/2), 사진 비율 6종, 대비 규칙(본문 4.5:1), 표 규칙, 숫자·결측 표기, 사진 캡션 '내용(연월)', 최소 글자 크기 원칙
("안 들어가면 글자를 줄이지 말고 나눈다"), 한국어 조판(`word-break: keep-all`, 제목 `text-wrap: balance`).

**벤치마킹 결과(P0 완료, 10-21 — `docs/catalog-benchmark-analysis.md`)**: 공개 브로슈어 7종 211쪽 실측. P1·P2에 추가로 넣을 요구:
- **사진 없는 변형 필수**: 표본은 쪽 절반 이상이 사진 50% 이상(대형사 전제). KESI는 전문 사진이 적을 가능성이 높아 모든 쪽 유형에 인포그래픽·숫자·지도·패턴 대체안을 둔다.
- **KESI 고유 모티프 1개**를 표지·간지·사진 틀·KPI 카드에 반복(대우의 아치처럼). P1에서 2–3안.
- **사업 분야 5색을 간지·쪽 머리에**(국가철도공단의 섹션별 옅은 색 방식).
- **번호 붙은 대표 사례 + 위치 지도**(한미 15선 방식) → C11.
- 국내 표본 5종 모두 PDF 링크·북마크 0, 1종은 글자를 윤곽선으로 변환 → 살아 있는 글자·북마크·목차 링크가 차별점.

## 4. 인포그래픽 라이브러리 — 자동 매칭과 사용자 선택 ★

사업 분야 쪽(C08·C09)뿐 아니라 C04·C10·C11·C14·A01에서도 인포그래픽을 적극적으로 쓴다. 현행 카탈로그의 광택 3D 4분면·그림자 도넛·
원형 다이어그램을 **같은 시각 언어(평면 도형 + 단색 선 아이콘 + 토큰 색)의 유형 라이브러리**로 대체한다.

### 4-1. 핵심 설계: "내용"과 "모양"을 분리해 저장

인포그래픽의 **내용은 중립 구조(Semantic Content)**로 저장하고, **유형(모양)은 그 구조를 그리는 방법**으로 따로 둔다.
같은 내용을 흐름도 ↔ 순환도 ↔ 기둥형으로 바꿔도 글이 사라지지 않는다.

```ts
// lib/catalog/infographic/types.ts (안)
interface InfoContent {
  title?: string;
  center?: { label: string; desc?: string };           // 허브형 중심
  items: Array<{
    id: string; label: string; desc?: string;
    value?: number; unit?: string; year?: number;       // 수치형
    icon?: string;                                      // lucide 아이콘 이름
    parentId?: string; group?: string; order?: number;  // 위계·묶음·순서
    region?: string;                                    // 지도형(시도·권역 코드)
    metricRef?: string;                                 // 데이터 바인딩(§6-4) — 숫자는 여기서만
  }>;
  compare?: { before: { label: string; value: number }; after: { label: string; value: number }; unit?: string };
}
interface InfographicSpec { type: InfoType; variant: string; content: InfoContent; colorMode: "brand" | "area" | "mono"; }
```

### 4-2. 유형 목록(1차 16종)

| 유형 | 내용 형태(필수 조건) | 항목 수 | 변형 | 주 사용처 |
|---|---|---|---|---|
| `process` 단계 흐름 | 순서 있는 항목 | 3–7 | 가로 화살표 / 세로 / 번호 원 | 허가 절차, 컨설팅 수행 방법 |
| `cycle` 순환 | 순서 + 순환 의미 | 3–6 | 원형 / 사각 루프 | 사후관리, PDCA, 자원순환 |
| `hub` 허브·방사 | 중심 1 + 가지 | 3–8 | 원형 방사 / 좌우 대칭 | 사업 분야 개관(현 4분면 대체), 자문위원 풀 |
| `pillars` 기둥 | 묶음별 하위 목록 | 2–5 묶음 | 기둥 / 카드 열 | 분야별 서비스, 핵심 역량 |
| `layers` 층위 | 위계·포함 관계 | 3–5 | 계단 / 피라미드 / 동심원 | 법·제도 → 서비스, 탄소중립 범위(Scope) |
| `matrix` 2×2·행렬 | 두 축 분류 | 4–9 | 2×2 / 3×3 | 업종×서비스 역량 |
| `timeline` 시간축 | 연월 있는 항목 | 4–14 | 가로 / 세로 / 연도 묶음 | 연혁, 사업 추진 경과 |
| `roadmap` 로드맵 | 단계 + 목표 시점 | 3–6 | 계단 / 화살표 띠 | 탄소중립 2030·2050, 고객 지원 로드맵 |
| `stats` 큰 숫자 | 수치 항목 | 2–8 | 가로 띠 / 격자 / 원형 강조 | 숫자로 보는 KESI, 분야 KPI |
| `compare` 전후 비교 | before/after 수치 | 1–3쌍 | 막대 / 화살표 수치 | 공급망 평가 58.4 → 87.0점 |
| `bar` 막대·순위 | 수치 + 범주 | 3–12 | 세로 / 가로 / 누적 | 업종별 실적, 연도별 수주 |
| `share` 구성비 | 합이 의미 있는 수치 | 2–7 | 도넛 / 100% 띠 | 인력 등급 구성, 분야별 비중 |
| `map` 지도 | 지역 코드 + 수치 | 5–17 | 권역(5) / 시도(17) 단계 구분 | 권역별 수행 실적(기존 d3-geo `RegionMap` 재사용) |
| `iconGrid` 아이콘 격자 | 목록(설명 짧음) | 4–12 | 3·4·6열 | 서비스 목록, 보유 역량 |
| `orgTree` 조직·체계 | 부모-자식 | 3–30 | 가로 트리 / 세로 | 조직도, 프로젝트 수행 체계 |
| `network` 협력 관계 | 중심 + 외부 기관 묶음 | 3–12 | 원형 / 좌우 | 협력 기관, 자문 네트워크 |

유형마다 **스키마 제약**(항목 수, 라벨 최대 글자 수 — 예: `process` 라벨 12자·설명 40자, 허용 변형, 최소 크기, 색 규칙)을 정의하고,
**같은 형태끼리는 무손실 변환**이 된다: 목록형(`process`·`cycle`·`pillars`·`iconGrid`·`hub`의 가지) ↔ 서로, 수치형(`stats`·`bar`·`share`·`compare`) ↔ 서로,
`map` ↔ `bar`. 형태가 다른 변환(목록 → 수치)은 막고 이유를 보여 준다.

렌더링: **정적 인라인 SVG + HTML**(d3-shape·d3-geo는 레이아웃 계산에만, ApexCharts 미사용) → 화면·PDF 동일, 글자는 SVG `<text>`가 아닌
HTML 텍스트로 얹어 PDF 텍스트 검색·복사가 되게 한다. 아이콘은 `lucide-react` 단색 선(현행 `public/icons/services/*.png`는 대체),
색은 `ink` 또는 영역 색 한 가지.

### 4-3. 자동 매칭 3단계

1. **형태 판별(규칙, 결정적)**: 내용 구조에서 후보 유형을 거른다.
   순서·단계어(→, 1단계, 접수·작성·협의…) → `process`/`timeline`/`roadmap`, 순환어(사후관리·반복·순환) → `cycle`,
   `center` 존재 → `hub`/`network`, `parentId` 존재 → `orgTree`/`layers`/`pillars`, `value` 다수 → `stats`/`bar`/`share`,
   `region` → `map`, `compare` → `compare`, `year` 존재 → `timeline`.
2. **적합도 점수(규칙)**: 항목 수가 유형 허용 범위에 맞는지, 라벨 길이가 넘치는지(실측), 놓일 슬롯 크기(전폭/반폭)에 맞는지,
   같은 섹션 안 다른 쪽과 유형이 겹치지 않는지(반복 회피), 같은 데이터 구조는 같은 도식(SR 규칙) 등.
3. **LLM 순위·이유(선택)**: 상위 후보 5개와 내용을 주고 의미 적합도를 매겨 짧은 이유를 받는다
   (feature `catalog.infographic_suggest`, Haiku급). LLM이 없거나 실패하면 2단계 점수만으로 정렬.

### 4-4. 사용자 선택 UI

- 스튜디오에서 인포그래픽을 선택하면 오른쪽 패널 **[유형 바꾸기]**에 **실제 내용으로 그린 미리보기 3–6개**(추천순, 추천 이유 한 줄)가 뜬다.
- 고르면 즉시 교체(실행 취소 가능), 변형(가로/세로·번호/아이콘)과 색 모드는 같은 패널에서.
- 넘침(라벨 길이·항목 수 초과) 시 경고 + **[AI로 줄이기]**(문구 축약) 또는 다른 유형 제안.
- 디자인 시스템 아티팩트에는 **인포그래픽 갤러리 보드**(16종 × 대표 변형, KESI 실제 내용)를 둬 사용자가 미리 보고 고를 수 있게 한다.
- 선택 기록을 분야별 기본값으로 저장(다음 생성 시 같은 분야는 같은 유형 우선).

## 5. 서체 선택·업로드 ★

서체는 문서의 인상과 가독성을 가장 크게 바꾸는 요소다. 그래서 **서체를 토큰처럼 갈아 끼울 수 있게** 설계하고,
**검증된 서체 세트 고르기**와 **새 서체 업로드**를 둘 다 지원한다. 단, 서체를 바꿔도 레이아웃이 깨지거나 가독성이 떨어지지 않도록 안전장치를 함께 둔다.

### 5-1. 역할별 서체 변수

- 디자인 시스템의 글자 토큰은 서체 이름이 아니라 **역할**을 가리킨다: `--kc-font-display`(표지·간지·쪽 제목), `--kc-font-body`(본문·표·캡션),
  `--kc-font-figure`(KPI 숫자·표 숫자·쪽 번호, `tabular-nums`). 컴포넌트는 이 세 변수만 쓴다.
- 서체를 바꾸면 변수 값만 바뀌고, 타입 스케일(크기·행간·굵기 단계)은 그대로다.
- 문서 단위로 고르고(`catalog_documents.theme.fonts`), 표지·간지 같은 쪽은 제목 서체만 따로 바꿀 수 있다(본문 서체의 쪽별 변경은 막는다 — 일관성).

### 5-2. 서체 세트(프리셋)와 비교

- 디자인 시스템에 **검증된 서체 세트 4–6종**을 둔다. 세트 = 제목·본문·숫자 서체 조합 + 굵기 대응표 + 크기 보정값. 후보(라이선스 확인 후 확정):
  - 모던 고딕: Pretendard(제목·본문)
  - 테크니컬: IBM Plex Sans KR(본문) + IBM Plex Sans(숫자) — SR 시스템과 같은 조합
  - 격조형: 명조 제목(예: 마루부리·Noto Serif KR) + 고딕 본문
  - 표준 고딕: Noto Sans KR / 나눔스퀘어 네오
  - 기존 보유 서체 활용: `frontend/public/fonts`의 KoPub 바탕(인사말·인용 강조용)
- 스튜디오 **[서체] 패널**: 세트 목록을 현재 문서의 실제 쪽(표지·사업 분야·부록 표)으로 그린 썸네일로 보여 주고, 두 세트를 **나란히 비교**한 뒤 적용한다.
  적용은 실행 취소할 수 있다.
- P2 목업에 **서체 비교 보드**(같은 쪽 3장 × 서체 세트 4종)를 넣어 기본 세트를 정한다(D2).

### 5-3. 새 서체 업로드

1. **올리기**: TTF·OTF·WOFF2(굵기별 파일 여러 개를 한 번에). 크기 상한(파일당 20MB).
2. **자동 분석**(서버, `@pdf-lib/fontkit`으로 파싱):
   - 이름 테이블 → 패밀리명·굵기(100–900)·기울임. 굵기 파일들을 한 패밀리로 묶는다.
   - **포함 허용(OS/2 `fsType`)** 확인: '포함 제한(Restricted)'이면 PDF에 넣을 수 없으므로 등록 거부, '미리보기·인쇄만'이면 경고와 함께 허용.
   - **글자 범위**: 한글 완성형 2,350자 기준 포함률, 영문·숫자·문서에 쓰는 기호(㈜ · → ○ ● ◐ ₂ ‘ ’ 등) 포함 여부.
     현재 문서에 실제로 쓰인 글자 중 빠진 글자는 목록으로 보여 준다.
   - **글자 꼴 수치**: unitsPerEm, x높이·대문자 높이, 한글 평균 글자 폭, 어센더·디센더 → 크기 보정값(§5-4)과 행간 보정 계산.
3. **용도 판정**: 굵기 400과 600·700이 모두 있고 한글 범위가 충분하면 '본문 가능', 아니면 '제목 전용'(장식·손글씨체는 사용자가 지정해도 제목 전용).
4. **라이선스 기록**: 출처, 라이선스 종류(OFL·무료 상업용·구매), 허용 범위(인쇄·PDF 포함·웹)를 업로더가 입력·확인해야 등록된다.
5. **저장**: S3 `catalog/fonts/{font_id}/…` 원본 + 미리보기용 WOFF2 변환본(converter의 fontTools). `catalog_fonts` 테이블에 메타 기록.
6. **견본(specimen) 화면**: 굵기별 한글·영문·숫자 견본, 본문 단락, 표, 큰 숫자를 실제 크기로 보여 준다.

### 5-4. 가독성·레이아웃 안전장치

- **크기 보정**: 서체마다 같은 pt에서 커 보이는 정도가 다르다(x높이·한글 폭 차이). `@font-face`의 `size-adjust`·`ascent-override`·`descent-override`를
  분석 수치로 자동 계산해 기준 서체(세트 기본) 대비 시각 크기를 맞춘다 → 서체를 바꿔도 넘침이 크게 늘지 않는다.
- 적용 직후 **전체 쪽 재조판 + 넘침 검사**(paginate 경고) → 넘친 쪽 목록과 [AI로 줄이기]·[원래 서체로] 선택지를 보여 준다.
- **가독성 규칙**(디자인 시스템 README에 명시하고 자동 검사): 본문 서체에 Light·Thin 금지, 본문 최소 크기 유지, 본문용으로 '제목 전용' 서체 선택 차단,
  명조 본문은 화면판에서 경고(인쇄판은 허용), 숫자 서체는 고정폭 숫자(`tnum`) 지원 여부 확인.
- **빠진 글자 처리**: 대체 서체(Pretendard)로 자동 보충하되, 보충된 글자 수가 많으면 경고.

### 5-5. 출력(PDF)에서의 서체

- 스튜디오 미리보기: 앱 경로(`/api/catalog/fonts/{id}/{weight}.woff2`)로 `@font-face` 로드.
- PDF 발행: converter가 해당 서체 파일을 받아 로컬 캐시에 두고, Playwright `page.route`로 정해진 내부 주소만 응답한다(외부 네트워크 차단 원칙 유지).
  Chromium이 PDF에 **사용 글자만 부분 포함(subset)**하므로 파일 크기 부담이 작다. 서체를 HTML에 base64로 통째로 넣지 않는다(한글 서체는 굵기당 수 MB).
- 발행본 스냅샷에 사용 서체 id·버전을 기록해, 나중에 서체가 교체·삭제돼도 같은 발행본을 다시 만들 수 있게 한다(삭제 대신 비활성화).
- 같은 서체 라이브러리를 홍보·채용공고 편집기(현재 Pretendard CDN 고정)에서도 쓰도록 열어 두는 것은 P8 확장.

## 6. 데이터 연결과 자동 갱신

### 6-1. 원칙: Pull(생성 시점 조회) + 발행본 스냅샷 + 변경 감지

- **초안(라이브)**은 열 때마다 DB에서 최신 값을 읽는다 → 계약·인사·회사 프로필이 바뀌면 초안은 항상 최신(사본 동기화 없음).
- **발행본(Edition)**은 발행 시점의 데이터 스냅샷 + PDF를 고정 보관한다(대외 제출 이력 추적).
- **변경 감지**: 주기 작업이 "현재 초안 데이터"와 "최근 발행본 스냅샷"을 비교해 **반영 대기 목록**(새 계약 3건, 입사 1명, 인증 1건…)을
  만들고 담당자에게 알린다. 담당자는 차이(diff)를 보고 발행한다. **대외 문서이므로 자동 발행은 기본 꺼짐**(D4).
- 1차 시도의 "이벤트 훅 불필요, 생성 시점 집계" 원칙을 계승하되, 사용자 요구("새 계약이 입력되면 자동으로 반영")를
  **초안 즉시 반영 + 알림**으로 충족한다.

### 6-3. 연혁 자동 후보

회사 프로필에 인증·특허·등록이 추가되면 **연혁 후보를 자동 생성**한다(사용자 요구: "회사 프로필 관리 정보 이용").
- `company_history`에 `category`(설립·등록·인증·특허·수상·조직·사업), `source_table`·`source_id`(멱등: 같은 출처는 1건),
  `is_public`, `highlight` 컬럼 추가.
- 자동 생성 규칙: `company_credentials` 저장 시 `issued_at`이 있으면 "YYYY.MM ○○ 인증 취득 / 특허 등록 / ○○업 등록" 후보를
  `is_public=true`로 넣는다(D6에서 '후보만'으로 바꿀 수 있음). 원본 수정·삭제 시 연동 갱신.
- 계약 기반 이정표(첫 ○○ 분야 수주, 누적 100건 달성 등)는 **후보 제안만** 하고 사용자가 채택.
- 화면: 회사 프로필 '주요 연혁' 카드에 출처 배지(인증·특허)와 공개 토글.

### 6-4. 실적의 대외 표기(부록 자동 생성의 핵심)

내부 `contract_title`은 그대로 대외에 쓸 수 없다. **대외 표기 메타**를 둔다.

- 신규 `contract_catalog_meta(contract_id PK, display_title, display_industry, is_public, is_featured, group_key, note, updated_by, updated_at)`.
- **기본값은 규칙으로 자동 생성**해 메타가 없어도 부록이 만들어진다:
  - 통합허가: 현행 문안 형식 재현 — `{발주처} {사업장} 통합환경허가 {최초/변경} 용역 준공({permit_issued_at}, 결정번호: 제 {permit_no}호)`,
    진행 중이면 "수행 중". 입찰 패키지 `buildOverview`(`lib/bid/package-data.ts:132`) 패턴 확장.
  - 업종: `facilities.industry_name` → `INTEGRATED_PERMIT_INDUSTRIES` 매핑.
  - 권역: `facilities.region_sido` → 5권역 매핑(코드 상수).
- **묶음 행**: 건수가 많은 분야(HAPs 586건, 화관법 216건)는 현행처럼 "기간·세부 업무별로 고객사를 묶어 한 행"으로 만든다(`group_key`).
- **노출 제외**: 비밀유지 고객은 `is_public=false`(총괄 건수에는 포함, 목록에는 "○○사"로 익명화 — D9).
- **대표 실적**(`is_featured`): 본편 C09·C11에서 쓰는 사례 후보.
- 기존 계약 백필: 규칙 생성 → 결과가 어색한 행만 LLM(`catalog.project_label`, Haiku)으로 대외 표기 제안 → 사용자 검토 화면에서 일괄 확정.
- 계약 입력 동선은 바꾸지 않는다. 메타는 별도 **[실적 노출 관리]** 화면에서 관리(신규 계약은 "미검토" 배지).

**분류 체계(D11 확정, 10-21)**: 부록·총괄표·사업 분야는 **계약 관리 5분류**(통합환경허가 / 장외·화관법 / HAPs / ESG·탄소중립 / 기타 용역)를 그대로 쓴다.
현행 카탈로그가 4분야인 것은 화관법과 HAPs를 한 표에 함께 나열했기 때문이며, 개편본은 둘을 나눈다. 분류 판정은 기존 `categoryCaseSql`
(`lib/ieps/contracts.ts`)을 그대로 써서 계약 관리 대시보드와 숫자가 일치하게 한다. 소개서에 보이는 이름만 바꿀 수 있게 표기명 필드를 둔다
(예: '기타 용역' → '환경 인허가·연구·교육').

**표시 범위 규칙(사용자 설정, 10-21 요구)** — 모든 계약을 다 실으면 부록이 불필요하게 비대해지므로, 사용자가 범위를 정한다.

| 규칙 | 설정 | 기본값(안) |
|---|---|---|
| 금액 하한 | 분류별 금액 기준(예: 500만 원 이하 미표시). 기준 금액 = 변경 반영 금액(`current_amount`), 없으면 `contract_amount`. 부가세 포함 여부는 계약 관리 기준을 따름 | 통합환경허가 0원(전부 표시), 그 외 500만 원 |
| 기간 | 최근 N년 또는 시작 연도 | 전체(2016~) |
| 상태 | 준공만 / 수행 중 포함 | 수행 중 포함("수행 중" 표기) |
| 금액 미정 계약 | 단가 계약 등 금액이 없는 계약의 표시 여부 | 표시 |
| 개별 고정 | 계약별 '항상 표시'·'항상 숨김'(`contract_catalog_meta.display_override`) — 대표 실적은 금액이 작아도 표시 | 자동 |
| 숨긴 실적 요약 | 분류·연도 끝에 "그 외 ○건(500만 원 이하)" 한 줄 표시 여부 | 표시 |
| 총괄표 집계 | 총괄표(A01)와 본편 KPI는 **표시 범위와 무관하게 전체 실적**으로 셀지, 표시된 실적만 셀지 | 전체 실적(실적 규모를 온전히 보여 줌) |

- 규칙은 문서(판)마다 저장한다(`catalog_documents.appendix_rules`) → 마스터본은 500만 원, 특정 분야 맞춤판은 다른 기준 등.
- 설정 화면에서 기준을 바꾸면 **표시 행 수·부록 예상 쪽 수가 즉시 바뀌어 보인다**(예: "500만 원 → 1,000만 원: 412행 → 268행, 부록 18쪽 → 12쪽").
- 묶음 행(HAPs·화관법)은 묶은 뒤의 행에 금액 합계 기준을 적용할지, 개별 계약 기준을 적용할지 선택(기본: 개별 계약 기준으로 거른 뒤 묶음).

### 6-5. 지표 정의 단일화

현행의 "99건 / 총괄표 괄호 109건" 같은 불일치를 없애기 위해 소개서 수치는 **지표 사전**(`lib/catalog/metrics.ts`) 한 곳에서만 계산한다.
각 지표: id, 라벨, SQL/계산식, 단위, 기준일, **정의 각주 문구**(쪽에 자동 표기 — SR 규칙). 예:
- `permit.initial.completed` **통합환경허가 최초허가 건수**(사용자 확정 10-21: 현행 99건이 정답, 총괄표의 109건은 오집계). 단위 '건'.
  현행 카탈로그 8장의 적용 차년도(업종군)별 내역(1차 발전·폐기물 31 · 2차 철강·비철 22 · 3차 석유화학 9 · 4차 제지·전자 8 · 5차 반도체 등 29 = 99,
  2026.6 기준)을 P4 대조의 기준값으로 쓴다. 이 표는 수주 연도가 아니라 업종군 기준이므로 업종 → 차년도 매핑(`INTEGRATED_PERMIT_INDUSTRIES`)이 필요하다.
  완료 판정은 `completions-status.ts`(허가일 또는 최종 계산서) 규칙. 총괄표(A01)의 괄호 숫자도 이 지표 하나에서 나온다.
- `permit.change.completed` 변경허가·변경신고 완료 건수
- `projects.total` 전 분야 누적 수행 건수(계약 기준)
- `staff.technical` 재직 기술인력 수(env_grade 기준)
- `market.permit.share` 환경부 통합허가 사업장 대비 수행 비율 — 분모(환경부 허가 사업장 수)는 외부 수치이므로 `catalog_external_figures`에
  출처·기준일과 함께 수동 입력
- 텍스트·인포그래픽의 숫자는 **반드시 지표 id로 바인딩**한다(LLM이 숫자를 지어내지 못하게 — §7).
- P4에서 현행 카탈로그 수치와 자동 집계를 대조하는 리포트를 만들고, 차이는 정의 결정으로 정리한다(D8 — 최초허가는 확정, 나머지 지표는 대조 후).

### 6-6. 개인정보

- 출력 옵션: **실명판**(수의계약·PQ 제출) / **마스킹판**(홍보·공개, 이름 가운데 글자 ○, 직원 사진 제외). 현행의 장마다 다른 마스킹(신0식/신○식/실명) 해소.

## 7. LLM 편집 — 디자인 시스템 안에서 내용을 고치고 더한다

### 7-1. 기능 키(`lib/ai/features.ts`, 그룹 `catalog` 신설)

| 키 | 용도 | 모델(안) |
|---|---|---|
| `catalog.section_write` | 사업 분야·핵심 역량·사례 쪽 문안 작성·수정 | Opus 5 |
| `catalog.page_compose` | **새 사업 분야 쪽 구성**(쪽 유형·인포그래픽 유형 선택 + 내용 구조화) | Opus 5 |
| `catalog.infographic_suggest` | 인포그래픽 유형 순위·이유(§4-3) | Haiku |
| `catalog.copy_fit` | 넘침 문구 축약·분량 맞추기 | Haiku/Sonnet |
| `catalog.project_label` | 실적 대외 표기명 제안(백필) | Haiku |

모두 `claudeMessages`/`anthropicChatJson` 게이트웨이를 거쳐 예산·킬스위치·사용량 기록이 자동 적용된다.

### 7-2. 흐름

1. 사용자가 쪽(또는 블록)을 선택하고 지시: "ESG 분야에 공급망 실사 대응 사례를 추가하고 인포그래픽을 5단계 절차도로".
2. 서버가 **컨텍스트 묶음**을 만든다: 현재 쪽 콘텐츠 JSON, 쪽 유형·인포그래픽 유형 스키마(허용 목록·글자 수 제한), 디자인 시스템의 콘텐츠 원칙
   (문체·최상급 금지·숫자 표기), 그 분야의 **지표 목록(id·값·정의)**, 대표 실적 후보 목록, 회사 기본 정보.
3. LLM은 **스키마에 맞는 JSON 패치만** 돌려준다(디자인·좌표는 건드리지 않음 — recruit `applyMapping` 원칙과 같음).
   숫자는 지표 id(`{{metric:permit.initial.completed}}`)로만 쓸 수 있고, 목록에 없는 숫자가 나오면 검토 표시.
4. 검증: 스키마·화이트리스트 sanitize → 글자 수 → 금지 표현(근거 없는 최상급) → 렌더 후 넘침 측정. 넘치면 `catalog.copy_fit` 1–2회 자동 축약 또는 유형 변경 제안.
5. **전/후 미리보기**를 나란히 보여 주고 사용자가 전체/부분 채택. 채택 시 버전 저장.
6. **새 사업 분야 추가**: 분야명·설명 메모·관련 계약 분류를 입력 → `catalog.page_compose`가 C09 쪽 구성(리드·서비스 목록·인포그래픽 유형+내용·KPI 지표 선택·대표 실적)을
   제안 → 같은 검토 흐름. 분야 색은 `area-n` 슬롯 중 빈 것을 배정.

### 7-3. 구현 메모

- 구조화 출력: ESG-KESI `services/llm.py`처럼 **JSON 스키마 구조화 출력**을 게이트웨이에 추가하는 것을 권장(현재 MCM은 프롬프트 → JSON 텍스트 → 수기 sanitize만 있음).
  1차는 기존 `anthropicChatJson` + 스키마 sanitize로 시작 가능.
- 결정적 대체안: LLM 없이도 쪽이 만들어지도록 규칙 기반 초안(`template_draft` 패턴 — 분야 지표·대표 실적으로 리드 문장 조립)을 둔다.

실측 함정(다시 밟지 말 것)
- **캔버스 검사는 배율을 풀고** — checkSheet 는 getBoundingClientRect(배율 적용)와 계산 padding(배율 미적용)을 섞어 쓴다. transform scale 상태로 재면 쪽 머리 글자가 모두 '여백 넘침'으로 잡힌다 → 검사 순간만 transform none.
- **iframe color-scheme** — 앱이 다크이고 틀 문서가 라이트면 Chromium 이 iframe 바탕을 흰 판으로 덮는다 → iframe 요소에 `color-scheme: light`.
- **react-dom/server 는 브라우저 판** — 칩·썸네일 정적 HTML 에 쓴다. 스튜디오 진입은 `next/dynamic(ssr:false)`.
- **contentEditable 칩** — 정적 렌더한 칩 요소에 `contentEditable="false"` 를 줄 때 `suppressContentEditableWarning` 필요.
- **color-mix 계산 색** — 계산 스타일이 `color(srgb …)` 로 나와 rgb 파서만 쓰면 대비가 거짓 경고된다.
- **CdHelp 는 p 안에 두지 않는다**(팝오버 div·ul 중첩 오류).

## 9. 렌더링·출력

```
스튜디오(브라우저): DocNode pages + 바인딩 값 + 위젯 → React 렌더 → paginate.js(같은 스크립트) → 화면 미리보기
서버 발행:          같은 React 컴포넌트 renderToStaticMarkup → 자체 완결 HTML(tokens.css·catalog.css·paginate.js 인라인, 서체는 내부 주소 — §5-5)
                    → converter POST /render/html-pdf(Playwright Chromium, 준비 신호 대기, page.pdf outline·tagged)
                    → PDF + 쪽 지도(앵커→쪽) + 쪽별 PNG(선택) → S3 catalogs/{YYYY}/{edition_id}/…
```

- **`paginate.js` 이식**: ESG 렌더러의 핵심(글꼴 로드 대기, 단·쪽 채우기, `data-split="rows"` 표 분할 + 머리 반복 + "(계속)", 각주 꼬리, 쪽 번호·링크 해결,
  넘침 경고)을 print-kit 으로 옮긴다. ✅ P4(10-22): ESG-KESI origin/main `f48d0bd` 기준 이식(출처 주석) — `frontend/public/print-kit/paginate.js`(스튜디오·서버 공용 한 파일).
- **converter 확장**: `POST /render/html-pdf`(HTML 본문 + 사용 서체 목록 → PDF). 기존 `/render/url-pdf`의 Chromium 설정 재사용. 보안상 페이지의 외부 네트워크 요청은 모두 차단하고
  서체·이미지는 `page.route`로 내부 주소만 응답(§5-5). 기본 서체 세트 파일은 이미지에 미리 넣어 캐시 적중을 높이고(현재 nanum·noto-cjk만 있음),
  업로드 서체 미리보기용 WOFF2 변환(fontTools)도 converter가 맡는다. ⚠ converter 재배포는 메모리의 주의 사항(전체 apply 금지·java-common 필수)을 따른다.
- PDF 위생(SR 교훈): 북마크(섹션→쪽), 태그 PDF, Title·Lang 메타, 내부 링크, **다른 PDF 엔진으로 재저장 금지**(링크 소실).

실측 함정(다시 밟지 말 것):
- **`@page { size }` 금지** — A4 가로 + `scale 4/3` 인쇄에 CSS 쪽 크기를 두면 Chromium 147 이 쪽 상자를 용지에 다시 맞춰 0.75배로 줄여 가운데 놓는다(ESG 원본에는 있었다).
- **서체는 TrueType 윤곽** — Skia 는 CFF(OTF·그 WOFF) 서체를 Type 3 으로 넣는다. Pretendard 를 fontTools cu2qu 로 TrueType 윤곽 WOFF 로 바꿔 두었다
  (`scripts/catalog/pretendard_otf2ttf.py`, 화면 차이 49,640px 중 5px) → PDF 에 `AAAAAA+Pretendard-Bold` 같은 부분 포함(Type0). 업로드 서체(P5b)도 같은 변환이 필요하다.
  ◐·前·現 처럼 Pretendard 에 없는 글자는 시스템 대체 서체로 그려져 Type 3 으로 남는다(모양은 포함되어 같다).
- **북마크용 숨은 제목** — `clip-path`·`display:none` 으로 숨긴 제목은 Chromium 이 북마크에 넣지 않는다. 투명 글자 1px(`.pk-outline`)로 둔다.
  쪽마다 h1(섹션, 섹션 첫 쪽만)·h2(쪽 이름)를 숨겨 두고 보이는 제목은 p 로 그려 북마크가 정확히 2단이 된다.
- **App Router 라우트에서 `react-dom/server` 는 막혀 있다**('react-server' 조건) — `print-kit/server.ts` 가 Node require 로 서버 렌더러를 연다. 쪽 컴포넌트는 훅·컨텍스트 없이 props 만 쓴다.
- 넘침 검사는 쪽 높이 외에 '쪽 여백 밖 글자'·'상자에 잘린 글자'·'칸 아래로 넘쳐 다음 내용과 겹치는 글자'·'칸 폭을 넘는 표'를 본다(겹침은 flex 칸이 줄어든 경우 — 쪽 높이로는 안 잡힌다).

**모티프 절제(사용자 지시 2026-10-22)**: "물방울·나뭇잎 모양이 너무 많이 쓰인다." → 물방울·잎은 상징 자리(표지·섹션 간지·뒤표지)에만 남기고,
본문 쪽은 장식 물방울을 빼고 요소 모양(쪽 머리 표식 → 세로 막대, 글머리·분야 점 → 원, 단계 번호 → 원, 아이콘 상자·카드·사진 틀 → 둥근 사각)을
평범하게 바꿨다(`lib/catalog/render/print-overrides.ts`). 디자인 시스템 README '모티프' 절과 목업에도 같은 규칙을 반영해야 한다.
- 판(variant) 옵션: 풀버전 / 요약본(부록 제외) / 실명·마스킹 / **분야 맞춤판**(선택 분야만 본편에 남기고 부록도 그 분야로 필터 — P8).
- PPTX: 1차 범위 밖(D7). 필요하면 쪽별 고해상도 이미지 슬라이드 + 노트, 또는 ESG의 PPTX 선택 트랙 결과를 보고 결정.

## 13. 검증 계획

- **수치 대조**: 자동 집계 vs 현행 카탈로그(통합허가 최초허가 99건과 차년도(업종군)별 내역, 변경 175건, 총괄 416·권역별·연도별, 인력 33명/기술 32명 등) — 차이 목록을 정의 결정으로 정리.
  최초허가 99건이 재현되지 않으면 원인(분류 누락·완료 판정·레거시 계약)을 계약 단위로 찾아 보고한다.
- **표시 범위**: 금액 기준 0 / 500만 / 1,000만 원에서 행 수·쪽 수 변화, '항상 표시' 계약이 기준 미만이어도 나오는지, 총괄표 숫자는 기준과 무관하게 같은지.
- **조판**: 모든 쪽 넘침 경고 0, 최소 글자 크기·대비 자동 검사, 실제 A4 컬러 출력 1부 육안 점검(인쇄판 본문 ≥10pt 규칙 확인).
- **PDF**: 북마크·내부 링크 동작, 텍스트 검색·복사, 파일 크기(사진 압축) 목표 ≤ 20MB, 생성 시간 목표 ≤ 60초(본편+부록).
- **자동 갱신 시나리오**: 계약 1건 등록 → 초안 부록 즉시 반영·반영 대기 1건 알림 / 임원급 입사 → 임원진 쪽 카드 추가 / 퇴사 → 즉시 제외 / 특허 등록 → 연혁·인증 쪽 반영.
- **편집 보존**: 자유 배치·문구 수정 후 데이터 변경·재생성해도 편집이 유지되는지.
- **서체**: 세트 4종을 차례로 적용했을 때 크기 보정 덕분에 넘침 증가가 미미한지, 업로드 서체(OFL 1종·포함 제한 서체 1종)의 등록 허용/거부,
  빠진 글자 경고, PDF에 서체가 부분 포함되어 다른 PC에서도 같은 모양으로 열리는지(1차 진단의 'OTF 서체 의존' 문제 재발 방지).
- **스튜디오 UI**: Precision 규칙대로 라이트/다크·1440/1024 폭·키보드 검증(문서 지면은 라이트 고정).
