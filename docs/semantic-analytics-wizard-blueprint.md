# 양식 요소 상관관계 설정 마법사(시맨틱 분석 위저드) 블루프린트 — 확정 v1.1

작성: 2026-07-30 · 확정: 2026-08-01. 상태: **§8 논점 6건 전부 권장안대로 확정. §4-4 경비 입력
채널 정책 추가(사용자 지시). SW-P0 착수.**

## 1. 배경과 문제 정의

전자결재 양식의 모든 항목은 이미 라벨링된 구조화 필드(`ApprovalFieldDef`: key + label + type)로 저장되고,
문서는 `approval_docs.field_values`(jsonb)에 필드 단위로 적재된다. 즉 **데이터는 이미 분석 가능한 형태로 쌓이고 있다.**
그러나 "이 필드가 무엇을 의미하는가"(출장 경비인지, 관련 용역인지, 수행 인원인지)를 시스템이 알지 못하므로,
필드들을 엮어 다음과 같은 파생 정보를 산출하려면 매번 하드코딩이 필요하다:

- 특정 용역(계약) 수행에 소요된 비용(특히 출장 경비) 집계 → **용역 원가·마진율**
- 특정 인원의 초과근무·근태·연간 수행 용역 수·평균 수행 기간 → **업무 성과 지표**
- 비용 절감 요소 탐색, 부서별 근태 상황 등

장기적으로 **클라우드형 그룹웨어 서비스(SaaS) 출시**를 염두에 두고 있으므로, 고객사마다 다른 양식·다른
분석 요구에 하드코딩으로 대응하는 것은 비현실적이다. **코딩 지식이 없는 관리자가 매뉴얼만 보고
①필드에 의미를 부여하고 ②요소 간 상관관계(연결 고리)를 확인·설정하고 ③원하는 지표를 조립하고
④실데이터로 즉시 테스트**할 수 있는 설정 마법사가 필요하다.

## 2. 현황 실측 — 이미 있는 것 / 없는 것

### 이미 있는 것 (재사용 자산)
| 자산 | 위치 | 이번 설계에서의 역할 |
|---|---|---|
| 필드 스키마(key/label/type 14종+) | `lib/approval/fields.ts` | 태깅 대상. jsonb라 **속성 추가에 마이그 불필요**(파서 확장만) |
| 엔티티 참조 필드 4종 | `contract_select`/`company_select`/`user_select`/`dept_select` | **조인 키가 이미 존재** — 값에 `{facilityId}`/`{contractId}`/`{employeeId}` 구조화 저장됨 |
| `fillMap`(자동 채움 규칙) | fields.ts `ApprovalFillRule` | "필드 간 관계"의 원형. 단 **입력 시점** 관계(값 복사)이며 분석 시점 관계와는 별개 |
| 양식별 문서 조회 + flatten | `/approval/records`, `/api/approval/query` | field_values → 표 변환 로직. 지표 엔진의 소스 평탄화에 재사용 |
| 결재 인사이트(하드코딩 지표) | `lib/approval/insights.ts` | 반려율·소요·체류 — 마법사로 만든 지표의 "코드 시드" 선례 |
| AX-P5 시맨틱 레이어 계획 | `docs/e-approval-differentiation-blueprint.md` §9-6 | **핵심 접점**: METRICS 카탈로그+SQL 조립 원칙. 본 마법사가 그 카탈로그를 "사용자 정의 가능"으로 확장 |
| LLM JSON 헬퍼 | `lib/ai/llm-json.ts` | 마법사 "자연어 → 지표 초안" 보조 |
| 마스터/시스템 데이터 | `contracts`(계약금액·기성), `service_participants`, `employee_profiles`, ADT 근태(`lib/adt/overtime.ts`), `annual_leave_ledger` | 결재 문서 밖의 분석 소스 — 카탈로그에 시스템 뷰로 등록 |

### 없는 것 (이번에 만드는 것)
1. 필드의 **의미(시맨틱) 태그** — "이 currency 필드는 출장 경비 성격의 비용이다"
2. 양식↔마스터↔시스템 데이터를 잇는 **관계 그래프의 가시화·진단**
3. 코딩 없이 지표를 정의하는 **지표 빌더**와 이를 실행하는 **조립식 SQL 엔진**
4. 실데이터로 계산을 검증하는 **테스트 샌드박스(미리보기+데이터 품질 리포트)**
5. 위 전체를 안내하는 **마법사 UX + 템플릿 갤러리**

## 3. 설계 철학 (SaaS 대비 3원칙)

1. **선언적 정의, 조립식 실행**: 사용자 설정은 전부 JSON 정의(선언)로 저장하고, SQL은 서버 카탈로그가
   조립한다. 자유 Text-to-SQL·자유 수식 eval 금지(AX-P5 §9-6과 동일 원칙 — 정확도·보안·테넌트 격리).
2. **태그가 계약(contract)이다**: 지표는 필드 key가 아니라 **시맨틱 태그를 참조**한다.
   고객사가 양식을 바꾸거나 필드를 추가해도, 새 필드에 같은 태그만 붙이면 기존 지표가 그대로 동작한다.
   (예: "출장비 지표 = `cost.travel` 태그가 붙은 모든 필드의 합" — 양식이 몇 개든 무관)
3. **모든 산출에는 근거·진단이 따라붙는다**: 지표 결과 옆에 "이 숫자는 어떤 문서 N건에서 나왔고,
   연결 누락 M건은 제외됐다"를 항상 노출. 일반 사용자가 결과를 신뢰·검증할 수 있는 유일한 방법.

## 4. 개념 모델 — 3계층

```
[계층 1] 시맨틱 태그   : 필드에 "의미" 부여          (무엇인가)
[계층 2] 관계 그래프   : 엔티티 참조로 문서를 연결     (무엇에 대한 것인가)
[계층 3] 지표 정의     : 태그+관계를 조합해 숫자 산출   (무엇을 알고 싶은가)
```

### 4-1. 계층 1 — 시맨틱 태그 (필드의 의미)

`ApprovalFieldDef`에 선택 속성 `semantic` 추가(fields.ts jsonb 확장, parseFields만 보강):

```ts
semantic?: {
  concept?: string;      // 표준 개념 태그 key (아래 사전 참조)
  costCategory?: string; // concept가 cost.*일 때 세부 분류 (여비교통비/숙박비/…)
}
```

**표준 개념 사전(concept catalog)** — DB 테이블 `semantic_concepts`(시드 + 관리자 편집 가능, leave_types 패턴 재사용):

| 그룹 | concept key 예 | 의미 | 자동 인식 |
|---|---|---|---|
| 엔티티 참조 | `ref.contract` `ref.company` `ref.employee` `ref.dept` | 관련 용역/업체/인원/부서 | **필드 타입에서 자동**(contract_select 등) |
| 측정값 | `cost.travel` `cost.expense` `cost.outsource` `amount.revenue` `quantity.hours` | 비용·수익·수량 | currency/number 필드에 사용자 지정 |
| 시간 | `when.occurred` `when.period` | 발생일·수행 기간 | date/period 필드에 사용자 지정 |
| 상태·분류 | `dim.category` | 분석 차원으로 쓸 분류 | select/radio에 사용자 지정 |

- 엔티티 참조 4종은 필드 타입만으로 **자동 태깅**(마법사가 제안, 사용자는 확인만). 사용자가 실제로
  붙여야 하는 태그는 대부분 "이 금액이 무슨 비용인가" 수준 — 매뉴얼 없이도 이해 가능한 난이도.
- 표(table) 필드는 **하위 열 단위**로 태깅(`tableColumns[].semantic`) — 출장 경비 내역표의 금액 열에
  `cost.travel`, 분류 열에 `dim.category`.
- 빌더 속성 패널에 "데이터 의미" 섹션 추가(드롭다운 2개). **fillMap과 나란히 두되 개념 구분 명시**:
  fillMap = 입력 편의(값 복사), semantic = 분석 의미(집계 근거).

### 4-2. 계층 2 — 관계 그래프 (자동 도출 + 진단)

관계는 **별도 설정 없이 태그에서 자동 도출**된다: `ref.contract` 태그 필드가 있는 양식의 문서는
해당 계약에 "귀속"된다. 사용자가 하는 일은 설정이 아니라 **확인과 진단**:

- **관계 맵 화면**(`/approval/semantics`): 양식들·마스터 데이터(계약/직원/업체)·시스템 소스(ADT 근태,
  수행인력)를 노드로, 참조 필드를 엣지로 그린 그래프. "출장신청서 → 계약" 엣지 클릭 시
  근거 필드와 연결 성공률 표시.
- **연결 진단**: "출장보고서 승인 문서 120건 중 계약 연결 108건(90%) — 미연결 12건 보기".
  미연결 문서는 클릭 → 문서 열람 → (권한자에 한해) 참조 필드 보정 입력 유도.
  **양식에 참조 필드 자체가 없으면** "이 양식에는 '관련 용역' 항목이 없어 용역별 집계에서 제외됩니다 —
  빌더에서 계약 검색 필드를 추가하세요" 안내(빌더 딥링크).
- 문서↔문서 관계(출장신청 → 출장보고)는 v1에서 **공통 엔티티 경유**(같은 계약+같은 기안자+기간 중첩)로
  간주하고, 명시적 문서 링크 필드(`doc_select` 타입)는 후속 확장으로 유보(§8-4).

### 4-3. 계층 3 — 지표 정의 (노코드 계산)

DB `metric_definitions`(key, label, definition jsonb, owner, 공개범위, version). 정의 JSON 2형태:

**① 집계 지표(aggregate)** — 한 소스에서 태그 기반 집계:
```jsonc
{
  "kind": "aggregate",
  "source": { "type": "approval_docs", "forms": "auto",   // "auto" = 해당 태그 가진 모든 양식
              "status": ["approved"] },                    // 승인 문서만(기본)
  "measure": { "agg": "sum", "concept": "cost.travel" },   // 태그 참조(필드 key 아님)
  "groupBy": ["ref.contract"],                             // 차원 = 엔티티/기간/분류 태그
  "timeBy": { "concept": "when.occurred", "bucket": "month" }
}
```
지원 집계: sum / avg / count / min / max / count_distinct. 소스 타입: `approval_docs` 외에
`system.*`(시스템 소스 카탈로그 — 코드가 제공하는 안전한 뷰): `system.contracts`(계약금액·기성 발행액),
`system.participants`(수행인력·수행 기간), `system.attendance`(ADT 초과근무), `system.leave`(연차 대장).

**② 복합 지표(composite)** — 지표들 간 산술 결합(같은 차원끼리):
```jsonc
{
  "kind": "composite",
  "dimensions": ["ref.contract"],
  "formula": ["contract_amount", "-", "travel_cost", "-", "other_cost", "/", "contract_amount"],
  // 토큰 배열 = 지표 key + 사칙연산 + 괄호만 허용(파서가 화이트리스트 검증, eval 금지)
  "format": "percent"
}
```

### 4-4. 경비 입력 채널 정책 ★ (2026-08-01 사용자 확정 — 본 시스템의 핵심 동기)

정확한 **용역별 경비 산정**(→ 용역 원가·마진율, 소요 경비·출장 횟수·용역 규모·기간을 종합한
수행 인력별 성과 지표)이 그룹웨어 자체 구축의 핵심 동기다. 다우오피스 시절에는
①양식 텍스트의 DB화 부재 ②**한 건의 지출결의서에 여러 용역의 출장 경비가 혼합** 적재되는 구조
때문에 용역별 소요 경비 산정이 불가능했다. 이를 구조적으로 해소하는 운영 정책:

- **출장에서 발생한 모든 경비는 지출결의서가 아니라 출장보고서의 '지출 내역' 표 필드에 입력**해
  출장보고서와 함께 상신한다. 출장보고서에는 `ref.contract`(관련 용역) 필드가 있으므로
  **문서 1건 = 출장 1건 = 용역 1건 귀속**이 성립하고, 경비→용역 매핑이 문서 단위로 자동 완결된다.
- **지출결의서는 비출장성 지출 전용**으로 축소: 사무용품비, 업무추진비(부서 회식비·탕비실 다과류
  구매 등) 등 특정 용역에 귀속되지 않는 지출만 제출한다.

**표준 '지출 내역' 표 필드 설계**(출장보고서에 부착, 빌더 표 필드 + 열 단위 시맨틱 태그):

| 열 | 타입 | 시맨틱 태그 | 비고 |
|---|---|---|---|
| 일자 | date | `when.occurred` | 지출 발생일 |
| 분류 | select(교통비/숙박비/식비/일비/기타) | `dim.category` | 경비 세부 분류 차원 |
| 내용 | text | — | 지출 내용 서술 |
| 금액 | currency | `cost.travel` | `sumColumn` 지정 → 합계 자동 |

**설계에 미치는 효과와 후속 장치**:
- `cost.travel`의 소스가 출장보고서로 일원화되어 템플릿 ①(용역별 출장 경비)·②(마진율)의 데이터
  품질이 **정책적으로 보장**된다 — 태그가 계약이고, 채널 정책이 그 계약의 이행을 담보한다.
- 관계 맵(SW-P1) 진단에 **채널 위반 감지** 포함: `cost.travel` 태그가 출장보고서 외 양식에서
  발견되거나, 지출결의서 분류에 출장성 항목이 남아 있으면 경고 표시.
- (후속, AX-P3 연계) `approval_form_policies` 사전검토 규칙으로 지출결의서 기안 시
  "출장 관련 지출은 출장보고서의 지출 내역에 입력하세요" 경고 — 정책의 입력 시점 강제.
- 실제 양식 개편(출장보고서에 표 부착, 지출결의서 분류 옵션 정비·안내문 추가)은 **빌더에서 수행하는
  데이터 작업**(SW-P0 코드 배포 후 태깅과 함께 진행, §7 참조).

**실행 엔진** `lib/analytics/metric-engine.ts`(서버 전용): definition JSON → ①태그로 대상 양식·필드
해석(폼 버전 스냅샷 존중) → ②field_values flatten(기존 query 로직 재사용, 표 필드는 행 전개) →
③조립식 SQL 실행 → ④composite는 차원 키로 조인 후 산술 → ⑤결과 + **진단 메타**(대상 문서 수·
제외 사유별 건수) 반환. AX-P5 NLQ는 이 엔진 위의 얇은 어댑터가 된다(§8-1).

## 5. 마법사 UX (`/approval/analytics/wizard`)

일반 사용자 대상 5단계 위저드. 각 단계는 "다음"을 누르기 전 실데이터 기반 피드백을 즉시 보여준다.

- **STEP 0 — 템플릿 갤러리**: "무엇을 알고 싶으세요?" 카드 선택.
  시드 템플릿: ①용역별 출장 경비 ②용역 원가·마진율 ③인원별 초과근무 현황 ④인원별 연간 수행 용역 수·
  평균 수행 기간 ⑤부서별 휴가 사용률 ⑥비용 항목별 월 추이. 템플릿 = 미리 짜인 definition + 필요한
  태그 목록. **+ 자연어 입력**: "용역마다 출장비가 얼마나 들었는지 보고 싶어" → LLM이 템플릿 매칭
  또는 definition 초안 생성(선택지 JSON만, §3-1 원칙).
- **STEP 1 — 소스 선택**: 템플릿이 요구하는 태그(`cost.travel` 등)를 가진 양식 자동 검색.
  없으면 "어느 양식의 어느 항목이 출장 경비인가요?" — 양식·필드 목록에서 클릭 지정(=이 자리에서
  태깅 수행, 빌더 안 가도 됨). 문서 상태 필터(승인만/전체) 선택.
- **STEP 2 — 연결 확인**: 관계 진단 요약("계약 연결 90%") + 미연결 처리 방식 선택(제외/별도 표기).
  참조 필드 부재 시 빌더 딥링크 안내.
- **STEP 3 — 계산 정의**: 집계 방법·그룹 차원·기간 버킷을 문장형 UI로:
  "**[출장 경비]**를 **[합계]**로, **[관련 용역]**별, **[월]** 단위로 집계합니다."(각 괄호가 드롭다운).
  마진율류는 "다른 지표와 결합" 토글 → 산술 블록 편집기(지표 칩 + 연산자 버튼).
- **STEP 4 — 미리보기·검증(테스트 샌드박스)**: 실데이터 read-only 실행 → 표+차트 미리보기 +
  **데이터 품질 리포트**(대상 문서 N건 / 태그 필드 빈값 M건 / 연결 누락 K건 / 이상치 후보 — 평균±3σ).
  샘플 행 클릭 → 원본 결재 문서 모달(근거 추적). 저장 시 이름·설명·공개 범위 지정.

**산출물 게시**: 저장된 지표는 ①`/approval/analytics` 지표 보드(표+ApexChart+CSV 내보내기, 기존
insights 화면 계열) ②홈 대시보드 위젯(기존 위젯 프레임 재사용) ③AX-P5 NLQ의 조회 대상으로 자동 편입.

## 6. 대표 유스케이스 검증 (요구 시나리오 → 본 설계로 표현 가능한가)

| 요구 | 표현 |
|---|---|
| 용역별 출장 경비 | aggregate: 출장 문서(승인) `cost.travel` sum, groupBy `ref.contract` |
| 용역 마진율 | composite: (`system.contracts`.계약금액 − Σcost.*) / 계약금액, 차원 `ref.contract` |
| 인원별 초과근무 | aggregate: `system.attendance` 초과시간 sum, groupBy `ref.employee` (또는 초과근무신청서 문서 기반 — 소스 선택으로 사용자가 결정) |
| 연간 수행 용역 수 | aggregate: `system.participants` count_distinct(contract), groupBy `ref.employee`, 연 버킷 |
| 평균 수행 기간 | aggregate: `system.participants` 수행기간(일) avg, groupBy `ref.employee` |
| 비용 절감 요소 | 비용 태그별·월별 추이 지표 + 이상치 후보 리포트(STEP 4 진단의 상시화) |

성과급 산정 본체(대상액×요율−기여 차감)는 기존 결정대로 별도앱 영역 유지 — 본 시스템은 그 입력이
되는 지표(참여·발행액·평점)를 셀프서비스로 조회 가능하게 하는 선까지(§8-3).

## 7. 단계 계획 (SW-P0 ~ SW-P4)

| 단계 | 내용 | 규모 |
|---|---|---|
| **SW-P0** | 시맨틱 기반: `semantic_concepts` 마이그 114(시드+관리 화면 `/approval/semantic-concepts`) + fields.ts `semantic` 파서 확장 + 빌더 속성 패널 태깅 UI(필드·표 열 단위). **+ 양식 개편 데이터 작업**: 출장보고서에 표준 '지출 내역' 표 부착·태깅(§4-4), 지출결의서 분류 옵션 비출장 항목으로 정비·안내문 추가 — 코드 배포 후 빌더에서 수행 | 소 |
| **SW-P1** | 관계 그래프·진단: `/approval/semantics` 관계 맵 + 연결 성공률·미연결 문서 리스트 + 시스템 소스 카탈로그 등록(`system.contracts/participants/attendance/leave`) | 중 |
| **SW-P2** | 지표 엔진: `metric_definitions` 마이그 + `lib/analytics/metric-engine.ts`(flatten 재사용·조립식 SQL·진단 메타) + 집계/복합 정의 실행 + 단위 테스트 | 중~대 |
| **SW-P3** | 마법사 UX: 템플릿 갤러리(시드 6종) + 5단계 위저드 + 테스트 샌드박스(품질 리포트) + 지표 보드·홈 위젯 게시 + LLM 자연어 초안(수동 버튼, 비용 통제) | 대 |
| **SW-P4** | SaaS 채비: 태그 사전·템플릿의 테넌트별 커스터마이즈 구조 정리 + 사용자 매뉴얼(마법사 인앱 도움말 포함) + 권한 스코프(§8-2 결정 반영) + AX-P5 NLQ 어댑터 통합 | 중 |

의존: SW-P0→P1→P2→P3 순차(각각이 다음의 전제). SW-P4는 P3 실증 후.
AX 트랙과의 순서 조정은 §8-1 결정에 따름.

## 8. 논점 — **전부 권장안대로 확정(2026-08-01)**

1. **AX-P5(NLQ)와의 통합 방식** ✅ 확정: 본 설계는 AX-P5의 "코드 고정 METRICS 카탈로그"를 "시드 + 사용자
   정의"로 일반화한 상위 집합. 권장 = **AX-P5를 별도 구현하지 않고 SW-P2 엔진 완성 후 그 위에 NLQ
   어댑터로 얹기**(중복 구현 방지). AX-P5 착수는 SW-P2 뒤로 조정.
2. **민감 지표 권한** ✅ 확정: 지표 공개범위 3단(작성자만/관리자/전체) + `ref.employee` 차원 포함
   지표는 기본 관리자 한정(`reports.nlq` 권한키 설계와 정합). 직급별 데이터 스코프는 AX 결정대로 후속.
3. **성과급 연계 깊이** ✅ 확정: 본 엔진은 성과 "지표 조회"까지만 담당, 산정·지급은 기존 별도앱 유지.
4. **문서 간 명시 링크**(`doc_select` 필드 타입) ✅ 확정: v1 제외, 공통 엔티티 경유(같은 계약+같은
   기안자+기간 중첩)로 시작. 지출결의↔카드내역 대사 등에서 후속 도입 가능성은 열어 둠.
5. **계산 시점** ✅ 확정: v1 = 실시간 조회(문서량 수천 건 수준). 스냅샷 배치는 속도 문제 실측 후 도입.
6. **태깅 주체와 시점** ✅ 확정: 기존 양식 5종+α는 구현 시 시드 태깅, 이후 신규 양식은 저장 시
   "미태깅 금액/날짜 필드가 있습니다" 소프트 안내(강제 아님).

## 9. SaaS 관점 메모 (장기)

- **테넌트 온보딩 = 태그 사전 + 템플릿 팩**: 신규 고객사는 표준 concept 사전과 업종별 템플릿 팩을
  받고, 자기 양식에 태그만 붙이면 지표가 살아난다 — 이것이 "하드코딩 세팅 없는 커스터마이즈"의 실체.
- **정의는 전부 export/import 가능한 JSON**: 양식(fields)+태그+지표 정의를 묶어 "설정 패키지"로
  내보내기/가져오기 → 고객사 간 복제, 파트너 구축 상품화 기반.
- **매뉴얼 전략**: 별도 문서보다 마법사 각 STEP 인앱 도움말(스크린샷 GIF)+템플릿 갤러리가 사실상의
  매뉴얼. 일반 사용자의 학습 경로 = 템플릿으로 시작 → 복제·수정 → 백지 작성.
